# Eumenesの長期記憶システム改善案

2026年10月9日。段階0（ドメイン構造・開発基盤）は実装済み。それ以降は提案。採用済みの公開契約や実装範囲を、この提案だけで変更しない。

段階0の実装構造と検証手順は [ドメイン構造](../src/domains/README.md)。共有の出典・snapshot形式は `src/contracts/` に残し、ドメイン間の型参照を循環させない。既存API・fixture・3本の移行SQLを維持した。Eumenesへの本接続、時間評価・記憶選択、公開Snapshotの更新、実モデル評価はこの段階では未実装。

2026年10月9日の追記（実装状況）: 本体で完結する部品は実装済み。`temporal`（時間判定）、`selection`（scope適用・必須/追加選択・利用根拠の再検証・公開版の更新判定・Checkpoint検査）、成立期間の精度の永続（migration 0004）、複数scopeの読み取り（`listStateScopes`）、ユーザー停止の保護（由来に依らない）、意味keyの辞書照合、抽出評価の値の意味採点。Eumenes側は、`continuity`（目的・決定・未解決事項）と`memory`（明示登録・停止・訂正・忘却・journal・採用時検証・利用記録）を新設し、対話に接続した（段階1）。到達段階は[検証状況](verification-status.md)。未実装は、実モデルadapterと実モデル評価、ContextStillのEpisode・深い想起、World・Consolidationの接続、公開版・Checkpointの対話への結線、Web UI（CLIとAPIのみ）。

Eumenesで、本人の情報を正しく覚え、話と仕事の続きを保ち、必要な過去へ出典付きで戻れる記憶システムを作る。現在の出典・採用・失効・忘却の基盤を維持し、その上に時間の扱い、必要な記憶の選択、安定した公開Snapshot、話題の継続を加える。

目指す価値は、背景の再説明、誤った想起、訂正の言い直しを減らすこと。記憶の件数や要約数を成功指標にしない。SAAAの長期記憶構想を到達点とし、Eumenesで動く単位ごとに検証する。World、Episode、Consolidationの機能を維持し、別の所有者と接続する。

## Eumenesと揃えるドメイン構造と開発基盤

### 現状の共通点と差

現状は業務責務と技術層を組み合わせた構成で、Eumenesと同じドメイン単位の所有構造にはまだ揃っていない。`state`、`recall`、`extraction`、`lifecycle`等に純粋な判断を分け、依存方向を試験で検査している。一方、SQL実装とその試験は`src/store`、公開契約は`src/contracts`に集まり、各ドメインの判断・保存・試験を一か所から辿れない。

| 項目 | 現状 | 改善方針 |
| --- | --- | --- |
| 業務判断とSQLの所有 | 純粋処理は責務別、SQLとSQL試験は共通store | ドメインごとに契約・判断・SQL・試験を近接配置する |
| ドメインの公開入口 | packageの入口はある。内部は個別ファイルを直接参照する | ドメインの公開入口と依存グラフを定め、別ドメインの内部参照を禁止する |
| 境界検査 | hygiene試験が層の依存方向と禁止機能を検査 | ドメイン境界と純粋・永続の境界を両方検査する |
| 整形 | 両方とも`oxfmt 0.71.0`。タブ、幅80、ダブルクォート、末尾カンマ等が一致 | 共通設定を維持し、fixtureや生成物の除外は各repoの用途に合わせる |
| 静的検査 | 両方とも`oxlint 1.86.0`。`correctness: error`と`--deny-warnings`が一致 | TypeScript、unicorn、oxcの共通設定を維持する |
| 型検査 | TypeScript `5.9.3`、strict、`noUncheckedIndexedAccess`が一致。本体には追加の厳格設定あり | 本体の厳格設定とEumenes互換型検査を併存させる |
| 検証の単位 | Memoryは全体verify。Eumenesはdomain指定と全体verify | domain指定、domain試験、全体verify、検証レポートを追加する |

EumenesのReact、JSX、画面・実機器用の検査は、画面を持たない記憶ライブラリの必須依存にしない。整形とlintの共通部分は設定差を検査できる形にし、更新時は両repoを同じ変更目的で確認する。設定を毎回隣接checkoutから読み込む方式にはせず、単独checkoutで開発・配布できる状態を保つ。

### ドメインごとの配置

業務ドメインは、`records`、`state`、`recall`、`extraction`、`projection`、`lifecycle`とする。`projection`は既存のview構成と再検証を一つの所有単位にまとめる。時間判定や選択を加える際は、既存ドメインでの責任を先に決め、独立した判断と公開契約が必要なら新しいドメインを追加する。

各ドメインの標準配置は次の形にする。不要な層の空フォルダーやHTTP controllerは作らない。

```text
src/
  domains/
    state/
      contracts/        型と入出力の規則
      service/          純粋な採用判断と状態遷移
      repository/       MemoryDbに対する同期SQL
      migrations/       Stateが所有するSQL定義
      test/             判断と実SQLiteの試験
      index.ts          純粋APIと型のドメイン入口
      sqlite.ts         永続操作のドメイン入口
    records/ recall/ extraction/ projection/ lifecycle/
  evidence/             共通の出典契約と引用検査
  canonical/            決定的な表現とdigest
  contracts/            共通契約と既存exportの互換入口
  infrastructure/
    sqlite/             MemoryDb、schema、seq、共通の依存辺と墓標
  index.ts              既存のpackage公開入口
  sqlite.ts             既存の永続package公開入口
```

共通化するのは、出典、認可入力、決定的表現、DBポート、単調seq、共通依存辺と墓標等の基礎に限る。共通層へ各ドメインの業務判断を集め直さない。migrationの並びとschema版は単一の組立て箇所が所有し、ドメインが勝手に版を進めない。

別ドメインへの参照は`index.ts`、`sqlite.ts`、公開contractsを通す。純粋なserviceからrepositoryや永続入口へ依存させない。RecallがRecordsを読むための操作や、Lifecycleが値を消す操作は、所有ドメインの限定した公開操作として設計する。他ドメインのSQLをコピーしたり、削除責任をLifecycleへ集めたりしない。必要な読み取り操作は一括で実行できる契約にし、境界を作るために大量の個別照会を増やさない。

ExtractionによるState採用、Lifecycleによる複数ドメインの忘却は、Eumenesの単一writerの同じtransactionで各公開操作を呼ぶ。業務上の拒否や保存の未適用を確認してから成功を返す。現行の冪等性、出典依存、忘却閉包、復元規則を移動の前後で保つ。

既存の`eumenes-memory`と`eumenes-memory/sqlite`の名前・型・挙動は維持する。内部ドメイン入口をpackageの新しい公開subpathにすることは必須にしない。新規domainの図だけで循環がないと判断せず、現行importを棚卸しして依存グラフを固定する。

### 境界を機械的に検査する

Eumenesの`domains.ts`と`boundaries.ts`の考え方を採用し、所有パス、公開入口、許可した依存方向を一つの定義から検査する。循環、未登録の業務コード、別ドメイン内部への直接参照、純粋層から永続層への参照を拒否する。型だけの参照も境界の対象とする。

検査はTypeScriptの構文解析とモジュール解決を使い、通常import、re-export、静的に解決できるdynamic import、設定したaliasを対象にする。相対importだけの検査をそのまま複製しない。解決できない動的な依存は許可対象を明示し、検査対象外の抜け道にしない。

ドメイン内のunit試験はそのドメインの内部を検証できる。別ドメインの内部へは試験からも依存せず、公開操作か公開された試験用ポートを使う。consumer試験は配布packageの公開面だけを使用し、忘却等の横断scenarioは別の所有単位で管理する。fixtureも所有ドメインを対応付け、共通runnerから同じ入出力を検査する。

既存の時計・乱数・環境変数・通信・外部依存の禁止、同期SQL、ホストによるtransaction所有のhygiene検査を維持する。ドメイン化によって、現在の決定的なコアの条件を弱めない。

### 検証コマンドと記録

Eumenesと同じ操作感に揃え、次のコマンドを提供する計画とする。現行の引数なし`bun run verify`は全体検証として維持する。

| コマンド | 対象 |
| --- | --- |
| `bun run format`と`bun run format:check` | 現行oxfmtの整形と非変更の検査 |
| `bun run lint`と`bun run lint:fix` | 現行oxlintの検査と明示的な修正 |
| `bun run test:domain -- state` | 指定ドメインが所有する判断・永続試験 |
| `bun run verify -- --domain state` | 指定ドメインの整形、lint、境界、型依存、所有試験 |
| `bun run verify:all`または`bun run verify` | 全ドメイン、横断scenario、公開面、Eumenes互換型検査、evalの型検査 |

domain指定でも依存先の型は検査し、影響を受ける利用側ドメインは明示的に追加検証する。共通契約、migration、依存境界、公開exportsの変更では全体verifyを必須にする。Eumenesの接続変更では、利用側domainとEumenesの全体verifyも通す。domain指定の成功を全体検証済みとは扱わない。

検証結果には、選択したドメイン、依存範囲、sourceのhash、ツール版、各工程の結果と時間を残す。検証中にsourceが変われば不成立とする。複数検証によるレポート競合は、実行IDごとの出力と排他で防ぐ。EumenesのmacOS固有FFIをライブラリの開発基盤へそのままコピーせず、対応環境とロックの寿命を定めて実装する。

verifyはsourceを変更せず、整形・lint修正は別コマンドにする。実モデルの品質と外部接続は明示的なlive評価へ分け、資格情報なしで決定的な全体verifyが通る状態を保つ。ライブラリには、Web buildやブラウザ試験より、配布物だけで動くconsumer試験と実SQLiteの復元scenarioを必須にする。

### 移行順と構造の受入

まず現行の所有パス・import・試験・fixtureを一覧化し、共通設定の一致と全体verifyのbaselineを記録する。続いてドメイン定義と検証コマンドを作り、Records、State等を一つずつ移す。既存入口のre-exportで互換性を保ち、各移動で公開consumerと依存する利用側を確認する。Extraction、Projection、Lifecycleの横断処理は、依存先の入口を整えた後に移す。新しい記憶機能は原則この配置に追加する。

構造の受入条件は、各業務コード・SQL・試験・fixtureの所有者が一意、別ドメイン内部参照と循環を検出、純粋と永続の境界が成立、旧公開APIとfixtureが同じ結果、忘却閉包と復元試験が成立、domain検証と全体検証の対象が説明できること。境界検査自体には、禁止importやre-export、aliasを使った違反を検出する試験を置く。

構造移行で既存SQLスキーマやmigration履歴を不要に変更しない。ドメイン化と記憶の意味変更は分けて検証する。配布先Eumenesから、本体の内部パスを参照させない。

比較の根拠は両repoの`package.json`、`.oxfmtrc.json`、`.oxlintrc.json`、`scripts/verify.ts`と、[Eumenesの境界検査](../../eumenes/scripts/boundaries.ts)、[現在のhygiene検査](../test/src-hygiene.test.ts)。ツール版は2026年10月9日のcheckoutでの値であり、将来の固定版を保証するものではない。

## 記憶の取り込みと訂正

### 即時反映と背景抽出

確定した原文を先に保存し、明示的な記憶操作、訂正、忘却は優先経路で処理する。通常のプロフィール候補や経験の整理は背景queueで進める。長いモデル呼び出しの間はwriterのtransactionを保持しない。

自然文の訂正対象が曖昧な場合、旧記憶を即座に上書きしない。現在入力を優先し、対象になりうる旧記憶の公開を一時保留して、照合する。保留は対象scopeとkeyに限定し、無関係な本人情報まで停止しない。自信のない候補ごとに質問せず、今の回答や仕事に必要な曖昧さだけを確認する。

背景抽出が遅れても、未処理の原文を最近の会話として使えるようにする。処理済みの原文位置と、今回の入力までの境界を記録し、最新の訂正が古いSnapshotに隠れないようにする。後から届いた古い抽出結果で、新しい訂正を置き換えない。

### 本人の事実と推測

明示された好み・事実、推定した傾向、出来事、第三者の主張を別扱いにする。「最近Rustの話が多い」は観測であり、「Rustが好き」として採用しない。モデル自身の過去の回答は、本人の事実や外部操作の成功の根拠にしない。

最初は明示操作を即時採用し、モデル抽出はpreviewまたは確認待ちにする。実モデル評価を通した情報種別から限定的に自動採用を有効化する。仮定・伝聞・別人情報・不明な対象は、現在の本人状態へ自動昇格させない。追加の意味検証モデルは比較候補とし、モデル同士の一致を独立証拠として数えない。

`semanticKey`や人物IDを、モデルが毎回作る自由文字列だけで決めない。少数の共通predicateと版付きの辞書、scope内の人物・対象ID、aliasを使い、未知の項目は未知として保持する。「メインIDE」「普段のエディタ」は候補として照合し、同じ単語でもProjectや期間が違う場合は統合しない。自動統合の誤りは、別々に残る重複より影響が大きいため、不明な統合を保留する。

### ユーザーが停止した記憶の保護

抽出由来かユーザー由来かにかかわらず、ユーザーが停止・撤回した操作を保護する。保護対象はprincipal、scope、subject、predicate、必要なら旧値に結び付ける。モデルが言い換えたkeyで回避しないよう、意味の照合にも接続する。

停止は可逆の利用停止、忘却は対象と依存派生物の消去として分ける。忘却後は内容や内容由来の識別子を新たに残して再登録を拒否する方式にしない。既存の出典・派生物IDの墓標で古いデータの復活を防ぎ、将来ユーザーが新しく伝え直した情報の扱いは保存・抽出設定と明示操作で決める。

## 時間と適用範囲

知った時点、成立した期間、記録順序を別に持つ。ホストが渡す`atMs`と対象時点を純粋な判定関数に渡し、現在有効、過去有効、未来予定、時点不明を区別する。現在時刻が本体へ隠れて入り込まない構成を保つ。

「9月からZedを使っている」を10月に聞いた場合、記録は10月、成立開始は9月である。日が不明なら月の精度を保ち、9月1日という確定日を作らない。成立期間の精度・不明・根拠を格納する契約を追加する。現在の回答は現時点の状態へ、過去の質問は当時の履歴へ戻る。期限切れは自動的な本文削除を意味しない。

「今回は短く」と「今後は短く」を分ける。ユーザー共通、Project、Task、Topic、今回の依頼を明示的に解決する。範囲不明の発言を共通Profileへ昇格させない。

複数scopeを使う場合は、ホストが認可した参照集合と各scopeの版を保持する。共通Profileを各Projectへコピーしない。適用可能な情報に矛盾があれば、現在の明示指示と指定された例外を優先し、解決できない必須制約は保留する。文脈の選択と認可判定を混ぜない。

## 今必要な記憶の選択

### 必須情報と追加情報

既存View v1とv2を保ち、選択を扱う新しい契約を追加する。新契約では次を分ける。

- 必須集合は、現在の依頼、適用される禁止・制約、進行中の目的・決定・未解決事項、必要な直近会話、未完了Toolの対応関係から構成する。
- 追加集合は、関連する好み、本人の背景、過去の出来事、資料、Episode、Worldの投影から選ぶ。
- 取得状況は、検索した範囲、未処理の原文、取得上限、選択した情報、省略した情報、未解決の不足を記録する。

すべてのStateを必須にしない一方、必須制約の検出を単純な関連度ランキングに任せない。対象範囲の適用条件を先に検査し、その後で追加情報を順位付けする。必須集合が容量に入らなければ、明示的に分割・再計画・保留する。追加情報は省略理由を残して削減できる。

### 段階的な想起

普段の会話は本人の小さな公開Profileと現在のTopic、最近の原文で続ける。「この前」「当時の理由」「9月の決定」等の要求がある場合や、必要な根拠が欠ける場合に過去を探索する。

1. 明示ID、期間、Project、人物、Topicで範囲を絞る。
2. Stateと会話原文の検索、外部Recordsの検索、ContextStillのEpisode検索をそれぞれの所有者へ依頼する。
3. 選んだ参照の本文を取り出し、引用と前後の必要な範囲を照合する。
4. 足りない場合だけ別の検索signalや追加検索へ進む。追加取得の初期上限は2段階とし、総時間・件数・token予算も設ける。実測で調整する。

Recordsは外部取得物専用のまま維持し、会話原文をRecordsへ複製しない。会話検索はconversationの公開操作を拡張する。本体はSourceRefを通して両方を同じ根拠形式で扱う。

初期順位は、明示参照、対象時点と範囲、語句一致、対象一致を優先する。単純検索で失敗する言い換えや関連づけのケースを集め、embedding、entity、graph、rerankerの追加効果を個別比較する。検索順位やモデルの自信を真偽の確信度に変換しない。

「見つからなかった」「検索を打ち切った」「根拠が古い」「関連する訂正が未処理」を区別する。限られた検索結果から、記憶自体が存在しないとは断定しない。

## 公開Snapshotと回答採用

### 安定したProfileとTopic

台帳の最新状態と、モデルへ公開するSnapshotを分ける。Profile、Project、Topicには不変の公開版と、その元になる根拠manifestを持たせる。原文の追記で毎回要約やProfileを作り直さない。

Context Compilerは、固定方針、安定したProfileとProject、TopicとCheckpoint、追記する会話Tail、今回の取得結果と訂正、現在入力をProviderの契約に合わせて配置する。記憶は固定位置にあっても参照データであり、命令権限を持たない。監査用のIDや版は本文と分ける。

Checkpointは、未解決事項、決定、参照、処理境界を失わない継続情報にする。モデルの要約には原典範囲を持たせ、決定的に生成した状態と区別する。Topic変更はfocusを変える操作であり、進行中Taskの取消や本人の共通情報の忘却にしない。

訂正・忘却・認可変更は公開の安定性より優先する。公開後の新しい肯定情報は次の公開区切りまで待てる場合があるが、旧情報を否定する訂正を同じ扱いで待たせない。

### 利用した根拠と必須集合の再検証

現在のstateRevision全体の一致は安全側だが、無関係な背景更新による取消が増える。新契約では、利用したsource、item、Snapshot、scopeの認可、Policy、必須集合を同じ採用transactionで再検証する。

単に「選んだitemの版が変わっていない」だけでは不十分である。新しい制約や訂正が追加された場合、古い参照集合を使った回答でも失効させる。必須集合、関連する訂正の処理境界、選択Policyの版、出典の失効世代を検査対象に含める。関係が不明な変更は保守的に失効させる。無関係な更新でも採用できることと、新しい必須制約を取りこぼさないことを対になる試験で固定する。

`prepareInTransaction`で入力とUsageReceiptを固定し、モデル処理はtransaction外で実行する。`settleInTransaction`で最新の根拠、queueのattempt、取消、Providerの利用可否を確認し、回答とReceiptを一緒に確定する。Receiptには本文を重複保存せず、参照ID、版、選択理由、公開版、実際に送った入力の識別情報を持たせる。

失効時の自動再生成は、別のattemptで新しい入力を固定し、初期上限1回とする提案。長い再生成や連続訂正では理由を示して保留する。旧回答を採用して待ち時間を隠さない。

Memory依存の本文は、初期接続では検証と保存の後に完成回答として公開する。現行Eumenesは`partials`を公開できるため、画面の途中表示と音声の消費経路も確認する。将来の先行表示・読み上げは、途中公開時の検査、訂正時の停止、既に公開した内容の扱いまで契約化して有効化する。

### 忘却と外部派生物

ホストの起動時には、最新の外部journalとDBを照合してからMemoryの読み出しとworkerを開始する。journalが不整合なら、該当するMemoryを利用しない。古いDBを復元した場合は、変更フィードのカーソルと外部投影の状態を再同期する。

忘却は、旧出典だけでなく、引用されなかった入力に依存した候補、State、Snapshot、Checkpoint、回答、待機job、外部WorldとEpisodeの参照まで伝える。外部の削除確認はpending、unverified、failed、confirmedを区別し、未確認の消去を完了と表示しない。停止設定に関係なく忘却を実行する。

外部派生物の登録辺は現行journalに含まれない。復元後の再登録と照合を、外部投影の利用再開より前に実施する回復契約を追加する。外部の派生物を消しただけで、ホストが保存した過去回答や音声も消えたとは扱わない。各所有者が本文・キャッシュ・再生待ちを回収する。

## 背景整理とWorldの接続

Consolidationは、入力範囲、原典版、出力、採否、処理位置を固定して再実行可能にする。対話を優先して中断・再開できるようにし、重い整理を毎回の回答待ちに置かない。この分離はLightMemのTopic単位の整理とsleep-time updateも参考になるが、Eumenesでの効果は個別に測る。[LightMem](https://arxiv.org/abs/2510.18866)

整理で得た要約や傾向は派生物として扱う。同じ原典の複製や再要約で根拠数を増やさない。矛盾や反例を残し、単発の会話を恒久的な習慣や因果関係へ昇格させない。背景整理による採用をユーザーの明示訂正より優先しない。

Worldは、観測、仮説、予測、結果を分けた投影として接続する。Hindsightの証拠と推論を分ける構成を参考に、原典から導いた理解を事実の追加正本にしない。グラフと再検討が有用かは、複数記録を結ぶ質問で比較する。[Hindsight](https://arxiv.org/abs/2512.12818)

既存の`ExternalDependent`と変更フィードを入口に使い、外部参照の現在性・利用可否・入力版・復元後の再同期を補う。ContextStillのEpisode生成をEumenes側に二重実装しない。連携先が使用不能でも、原文と本人状態を使う通常会話を継続できる構成を保つ。

## 実装順と受入

| 順序 | 本体とEumenesで進めること | 次へ進む条件 |
| --- | --- | --- |
| 0 現状固定と開発基盤 | 現行接続計画を改訂。ドメインの所有・依存・公開入口を定め、oxfmtとoxlintの共通設定、domain検証、全体検証を整える。配布packageの版・hash・migrationを固定し、原文参照と公開操作を対応付ける | Eumenes単独checkoutで配布物を利用でき、所有境界と公開APIの互換性を試験で確認できる |
| 1 会話で一巡 | Eumenesにmemory接続層と最小continuityを作る。明示登録、想起、訂正、停止、忘却、採用時検証、journalを接続 | 隔離DBの実会話経路で一巡し、生成中訂正・取消・古いDB復元でも旧情報を採用しない |
| 2 選択と時間 | 複数scope、必須集合、追加選択、時間照会、意味keyの照合、ユーザー停止保護を追加 | 無関係な記憶を省きながら必須制約を保つ。現在・過去・今回だけを区別する |
| 3 継続と公開 | Profile、Project、Topic、Checkpoint、Tail、公開版、利用依存の再検証を追加 | 同Topicで不要な再生成が減り、話題を戻しても未解決事項が残る。訂正は即時反映する |
| 4 自然文の記憶 | 実モデルadapter、意味を採点する評価、訂正候補の優先処理、情報種別ごとの自動採用を追加 | 人手確認した正解と固定した基準で評価し、誤本人化・否定逆転・期間混同を満たす種別だけ有効化する |
| 5 深い想起 | ContextStillのEpisode、時間・人物・Topic検索、必要性を示したembedding等を接続 | 単純検索との差を、正解、根拠、時間、入力量、費用で説明できる |
| 6 背景整理とWorld | 外部ConsolidationとWorldを接続し、訂正・忘却・回復を通す | 整理ありとなしを同条件で比較し、想起と継続の改善を示す。派生物を独立根拠として加点しない |

各段階は機能を廃止する境界ではなく、検証を積む順序である。抽出評価や検索の失敗分析は、初期接続と並行して準備できる。実装の存在、本体契約の成立、Eumenes結合、モデル品質、実機器・連続運用は別に記録する。

実装時の確認は、本体で変更したdomainのverifyと利用側domainの試験、横断変更で`bun run verify:all`を使う。domain検証の追加前は現行の`bun run verify`を使う。Eumenesで変更したdomainのverifyと`bun run verify:all`を通す。実モデル評価と実音声は別laneとし、credentialがなくても決定的な結合試験が通る構成にする。計画の作成だけで検証段階を上げない。

## 改善を測る基準

最初に、記憶なしの有界履歴、現行のState投影、選択と公開Snapshotを加えた方式を同じ入力・モデル・初期状態で比較する。その後、Episode、検索signal、Consolidation、Worldを一つずつ足す。大きな履歴を全部送る方式は評価用の比較対象とし、日常の必須経路にしない。

抽出、検索、選択、原文読解、回答生成を分けて採点する。モデルの自己評価だけで合格を決めない。合成の日本語会話を使い、人が確認した対象・値・極性・適用範囲・成立期間・出典の正解を持つ。LLM採点を補助に使う場合も、不一致と危険な誤採用は人が確認する。

LongMemEvalの抽出、複数会話、時間、更新、回答不能の五つの能力を参考に、Eumenesには訂正・忘却・scope分離・音声公開の試験を加える。[LongMemEval](https://arxiv.org/abs/2410.10813)

| 評価すること | 受入シナリオと観測 |
| --- | --- |
| 正しく覚える | 「嫌い」を「好き」にしない。別人・引用・仮定を本人の事実にしない。属性だけでなく保存した値の意味を採点する |
| 正しく思い出す | 判断理由と当時の原文へ戻る。原文を取得できなければ不足と答え、存在しない記憶を補わない |
| 時間を区別する | 「昔はA、今はB」「9月からB」「今回はA」を、現在と過去の質問で使い分ける |
| 話と仕事を続ける | Topic AからBへ移り、再起動を挟んでAへ戻っても目的・決定・未解決事項を保持する |
| 訂正を優先する | 抽出待ち・生成中・回答採用直前の訂正で旧値を使わない。古いjobが新しい訂正を上書きしない |
| 忘却を保つ | Memory OFF、遅着job、古いDB復元、外部派生物、表示・音声の待機中を通して再利用されない |
| Scopeを保つ | Project A限定の情報をBへ混ぜない。共通Profileとの併用は許可した範囲で成立する |
| 入力と待ち時間を抑える | 同Topicで10〜20turnを比較し、公開版の変更数、追加検索回数、token量、p50/p95、実cached tokensを記録する |

危険な誤採用、scope漏れ、忘却後の復活は、固定した受入セットで0件を必要条件とする。0件は一般の無誤りを保証しないため、件数と信頼区間も示す。意味の正しさを満たした上で、成功した回答あたりの時間とtoken費用を比較する。改善幅や性能上限はbaseline取得後、最終評価の前に固定する。

実cached tokensを取得できなければ未計測とし、Prefixが一致しただけでcacheが効いたとは扱わない。実運用で評価する場合も、通常ログに会話本文を出さず、ユーザーの保存設定に従う。テスト用fixtureとモデル評価には製品DBや実会話をコピーしない。

## 最初に着手する範囲

最初にドメイン所有と依存境界、Eumenesと共通の整形・lint方針、domain検証と全体検証を整え、既存の純粋APIと永続APIを保って構造を移行する。Eumenesへの接続実装は、この基盤に沿って進める。

最初の接続実装は、現行Eumenesに合わせた接続計画の改訂、版を固定した配布物、conversationの出典操作、最小continuity、MemoryClient、採用transaction、忘却journalの接続とする。ここで実会話の一巡を成立させる。

同時に、新しい選択契約と時間判定の設計、値の意味を評価するデータを準備する。初期実装で大型のベクトルDB、専用queue、外部Memoryサービス、自己学習による採用Policyを必須にしない。これらは不足と改善を示してから選ぶ。World、Episode、背景整理の到達点は維持する。

設定には、履歴を保存する、本人情報を抽出する、応答へ記憶を使う、外部Episodeを利用する、背景整理を行う、を区別する。候補は一括で確認でき、今の仕事に関係する曖昧さだけを会話で尋ねる。ユーザーが「何を覚えている」「なぜそう理解した」「訂正」「忘れて」に答えられる最小UIを、最初の実利用接続に含める。

残る採用判断は、実モデル評価前の自動採用範囲、Category別の合格基準、外部連携と保存の初期設定、実測に基づく検索・公開・再生成予算。候補案を比較できる状態にしてから判断し、既存設定を変更した扱いにしない。

根拠となる構想は[SAAAの全体コンセプト](https://chatgpt.com/space/page_9fc5877949748191b556705128f6a2f5)の記憶とContext、World、訂正・忘却。既存の[全体設計](full-system-design.md)と[接続計画](../../eumenes/spec/memory-system-incremental-adoption-concept.md)は、採用時に新しい範囲と現行コードへ整合させる。
