# Eumenes Memory 技術品質80点到達の改善計画

作成日: 2026年11月5日。実行予算は同日の利用者指定により10 USDへ変更。基準コミット: `f0357dcf1341af6bb5464729f3251b4f266575b4`。

現行の技術品質評価71.1点から、同じ評価尺度で80点以上を実証する。既存の不具合修正に加え、配布物の継続検証、入力と障害の境界検証、導入・復元手順、性能と費用の実測を進める。Claude APIとOpenAI APIのLunaは、既存の記憶処理を評価するホスト側で利用する。

## 1. 評価基準と完了条件

前回と同じ rubric 1.1.0、library profile、deep、全30技術基準と配点を使用する。対象機能・適用基準を狭めたり、合成ケースの正解や試験期待値を変更したりして80点に合わせない。プロジェクトの価値・将来性は別の評価であり、今回の80点目標と混ぜない。

前回は技術基準の98.3%を確認し、性能予算だけが未確認だった。最終判定では100%を確認する。現在の暫定71.1点と、確認範囲が増えた後の正式点の差を、そのまま実装改善量として扱わない。

- 最終コミットに対する正式な技術品質が80.0点以上。未解決のCritical／High、および未調査の重大疑義がない。
- F01とF02の再現試験が変更前に失敗し、変更後に通る。既存の正常利用・権限境界・忘却を維持する。
- 部分試験、結合試験、配布物だけを使う通し試験、実API評価、最終全体検証が通る。
- 全体検証と最終API評価の間で製品ソースが変わらない。変更した場合は影響する結果を無効化し、同じ条件で再検証する。

## 5. Claude APIとOpenAI Lunaの使い分け

| 接続 | 初期設定案 | 役割 |
| --- | --- | --- |
| OpenAI API | Responses API、`gpt-6-luna`、reasoning effort `medium` | 現行モデルを維持した生成・保存計画・取得・回答の主評価。Claude生成物の意味評価も担当 |
| Claude API | Messages API、`claude-sonnet-5-5`。effortはpilotで対応値を確認して固定 | 同じケースで生成を比較し、Luna生成物を別providerで意味評価。失敗候補と曖昧な正解の点検 |
| 人による裁定 | 正解と採点規則を理解した確認者 | 評価器の不一致、危険な誤り、曖昧な正解の裁定。都合のよいモデルの票を採用しない |

モデル名・API・SDK版・effort・価格表・実行時刻・返却モデル情報をmanifestに固定する。利用可能なら不変のsnapshot IDを使い、提供されない場合はその限界を記録する。モデルが利用不可でも黙って別モデルに替えない。Claude Sonnetの設定に対応しない`temperature`等を共通引数として送らない。

現在の`luna.ts`はCodex SDKを使用しており、OpenAI API直接利用と同じ測定条件とは限らない。当初案では20ケースをCodex SDK／Responses APIで各2反復する。ただし今回の10 USD実行では、Codex SDK経路に予約可能な最大出力・請求上限を強制できないためSDKへの有料再実行を保留し、既存のSDK固定試験とAPI直接経路の新baselineで指示・入出力契約と差を記録する。差があれば直接APIの新しいbaselineを作り、過去の77→92件という成績や時間を、そのまま新接続の基準に流用しない。既存のCodexチャットへメッセージを送る方式は使わない。

### 共通アダプターの契約

- `Complete(prompt, schema, task)`を再利用し、`decide`／`recall`／`judge`の高権限指示を各APIへ正しく渡す。新しい評価タスクが必要なら評価側で契約を明示し、本体へ移さない。
- OpenAIはStructured Outputs、Claudeも構造化出力を使用する。API間で対応するJSON Schemaが異なるため、providerへ送るschemaと、実行前に検査する正本の契約を分ける。
- Claudeで非対応の数値・長さ・件数制約は、送信用schemaから仕様に従って変換しても、ホスト側の正本validatorには残す。意味分類や不正IDの補正は追加しない。
- APIが整形式を返しても、許可ID、件数・長さ、引用、principal／scope、CAS、journal状態を既存機構で再検査してから適用する。
- 応答の拒否、上限到達、未完了、schema違反、意味失敗、通信失敗を別の状態として記録する。拒否や空応答を、正常な「該当なし」へ変換しない。
- `threadId`は既存型が許す`null`にできる。API request／response IDは別の評価記録へ保存し、Codex thread IDとして偽装しない。
- usageは原形式も保持し、入力・出力・cache read／write・reasoning等を可能な範囲で分ける。報告されない値を0に置かない。
- 新しいAPI依存は開発用に固定する。既存の実験記録に埋め込まれたMODEL／SDK定数を、新providerの実行結果へ誤って記載しない。

## 6. 評価データと実験方法

### ケースの分離

開発用40ケースを診断・指示修正に使用する。最終判定には、新規holdout120ケースと既知回帰80ケースを用い、各provider・旧新の2方式を各3反復する。holdoutは開発用と意味構造・正解の重複を点検し、単なる固有名詞の置換を新規問題として数えない。

新規120ケースは24の意味・失敗パターンから各5ケースとする。人物の帰属、否定の範囲、頻度・数量、時点・条件・例外、訂正・共存・矛盾、曖昧な対象、同義の別キー、部分回答、引用内の命令、忘却の例外、長い無関係文脈などを含める。試験対象のモデルに、そのモデル自身の採点用正解を決めさせない。ケース案の生成にモデルを使っても、正解・許容根拠・失敗条件を人が事前に確定する。

旧新の指示・実行条件が同じhashなら、重複する2方式の比較は省き、両providerの固定回帰と境界検証を実施する。以下の呼び出し数は2方式を本当に比較する場合の最大枠であり、改修していない意味処理の改善を演出するためには使わない。

危険な操作や権限境界は、意味ケースとは別に実SQLiteと決定的な対照で確認する。APIには合成データを使用し、既存の実会話・seed本文・資格情報・私有ソースを自動送信しない。

### 生成と採点を分ける

1. 原発話→計画→適用→実際のDB状態を検査し、対象・操作・主体・極性・条件・根拠を確認する。
2. 保存済みの固定snapshotから取得し、回答項目ごとのsupported／unknown／conflictと根拠IDを照合する。
3. 自然文の最終回答は評価用ホスト工程として別に生成する。現在の公開APIが最終回答まで保証するような説明はしない。取得IDが正しくても回答が誤る場合を別集計する。
4. 正しい保存結果を与える条件と、モデルが生成・保存した結果を与える条件を分け、保存・取得・回答のどこで失敗したかを追えるようにする。
5. 完全一致で判定できるID・操作・状態・引用・数値制約はコードで判定する。日本語の同義性・含意・条件保存はモデルと人が判断し、語句の辞書や正規表現へ置き換えない。

各試行の追加モデル呼び出しは最大2回とする。複数ターンの通しシナリオは小規模の別枠とし、回数・費用を個別に見積もる。無制限の会話長を主評価へ混ぜない。

### 評価器の校正と盲検

先に40組の既知の正誤対照を作り、ClaudeとLunaの評価を確認する。同義・条件欠落・人物誤り・否定の反転・関係の飛躍・数量の弱化・裏付けのない断定を含める。評価器の合否一致率95%以上、危険な誤りを合格にする件数0を開始条件にする。満たせなければ校正方法を見直し、その評価器を本試験の合否決定に使わない。

自然文評価用40ケースを、出力を見ずに層別固定して主評価から選ぶ。両providerの生成物を、両providerが評価する交差表で保存する。方式名・生成providerを隠し、比較順を固定seedで反転させる。同一providerによる自己評価と、別providerによる評価を区別する。評価器は再現可能な正解ではなく、誤る観測器として扱う。

不一致は原応答と根拠を保持して人が裁定する。合意するまでAPIを引き直さない。裁定できないものは未確定として残し、成功に数えない。正解不備が見つかった場合は元の成績も残し、改訂データの新規実験として扱う。

### 採用条件

- 権限外の読取・適用、指定外の忘却、忘却後の復活、固定の漏えいsentinel出力は試験集合で0件。1件でもあれば候補の採用を止める。0件は一般的な無事故の保証ではない。
- 新規holdoutの主指標は試行全体の契約・状態・根拠の合格率。各反復とパターンを明示し、120×3を独立した360問題として扱わない。
- 初期目標はLunaの新規holdout合格率95%以上、自然文回答の根拠を越える断定0件。既存baselineが未達なら、その差と原因を改善対象にする。Claudeは同じ基準で測るが、単にLunaより高いという理由で標準モデルを変更しない。
- 候補の改善を主張する場合は、事前固定した対応比較で新規の純増5ポイント以上、パターン単位の片側検定でp≤0.025を要求する。最大2候補の比較を前提とした値であり、最良の試行だけ選ばない。
- 既知回帰は安全性に新規悪化0件。一般品質はbaselineとの差の片側95%区間の下限が−2ポイント以上を目標とし、パターンを単位に算出する。件数不足で判定不能なら非劣性確認済みと書かない。
- 絶対的な性能予算を満たし、候補のp95遅延は対応baselineの1.15倍以内、API費用は1.10倍以内。精度向上との交換条件を事後に変更しない。
- 指示変更が必要なく現行方式が条件を満たす場合は、その方式を維持する。評価基盤を導入したこと自体を意味精度改善と呼ばない。

## 7. 性能と費用の予算

| 対象 | 初期の受入値案 | 測定方法 |
| --- | --- | --- |
| DB読取・1000件列挙 | p95 100ms以下 | 固定環境、cold／warmを分離、各条件30回以上 |
| 単件保存・1000件規模の閉包忘却 | p95 200ms以下 | 線形・分岐・共有依存のグラフを別測定 |
| 評価ホストのメモリー | peak RSS 512MiB以下 | DB処理・API待ち・入力構築を分離 |
| Lunaの取得＋回答 | 全工程p95 20秒以下、費用0.03 USD／問以下 | 逐次実行を主測定、並行2の結果も別掲 |
| Claudeの取得＋回答 | 全工程p95 30秒以下、費用0.35 USD／問以下 | 同じ論理入力。providerごとのtoken数は別計測 |
| 出力上限 | 1問の全工程合計4096 output tokenを初期値 | reasoningを含む実usageを記録。不足・打切りは失敗として計上 |

全記憶一括方式が予算を満たすなら維持する。満たさない場合は、既存の凍結ページ方式やLLMによる候補取得を比較対象として再利用する。索引を永続化する変更は、更新・忘却・復元への追従を実証できるまで導入しない。1000件からの黙った切捨て、失敗をunknownへ変える処理、意味を判断するキーワード分岐は加えない。

## 8. API費用と実行制御

初回の費用上限案は **合計10 USD**、うちpilot・校正に最大1 USDを割り当てる。これは計画上の予算案であり、今回の有料実行や追加支出は発生していない。pilotの実token量から主評価の総額を再見積もり、10 USD以内に収まらなければ本試験の開始前に対象・回数または予算を見直して再固定する。

2026年11月5日に確認したStandardの単価は、Lunaの短い文脈では入力0.10／出力0.50 USD、Claude Sonnet 5.5は入力2／出力10 USD、いずれも100万tokenあたり。Lunaの長い文脈では入力0.20／出力0.75 USD。cache read／write、長文条件、地域加算、請求対象のreasoning、利用する処理tierを価格表へ別記する。予算見積りではcache割引とBatch割引を前提にしない。時間測定にBatchの値を混ぜない。

費用は「uncached入力×単価＋cache read×単価＋cache write×単価＋課金対象出力×単価」で計算する。providerの原usageと重複計上しない。usage欠落があれば、予約上限額を解放せず不明額として報告する。

| 評価枠 | 呼び出し上限の計算 |
| --- | --- |
| pilot | 12ケース×2provider×生成・交差評価各1回＝48回 |
| 評価器校正 | 40対照×2provider＝80回 |
| SDKからAPIへの移行確認 | 20ケース×2接続×2反復＝80回 |
| 開発用 | 40ケース×2provider×旧新2方式×最大2呼出し＝320回 |
| 最終主評価 | 200ケース×2provider×旧新2方式×3反復×最大2呼出し＝4800回 |
| 自然文の交差評価 | 事前固定40ケース×2生成provider×旧新2方式×3反復×2評価provider＝960回 |
| 合計 | 最大6288回。予備を含む全API試行の上限6500回、費用上限も同時適用 |

呼び出し数は上限であり、全枠を必ず消費するものではない。tokenの多い長文試験は件数と別に予約する。性能試験・裁定補助・再試行も、同じ6500回／10 USDの枠から差し引く。主評価の反復を一部だけ実施して、予定全件が完了したように報告しない。

各dispatch前に最悪費用を予約し、実費精算後に残枠を更新する。入力・出力・件数・金額・同時実行・時間の上限をコードで強制する。初期同時実行はproviderごとに2、request timeoutは120秒とし、アカウントの制限をpreflightで確認する。

429・一時5xx・接続失敗はRetry-Afterを尊重し、最大2回の再試行まで。認証・schema・設定エラーは再試行せず停止する。通信失敗が3回続いたら新規dispatchを止め、進行中の応答を回収して状態を保存する。正常に動作中の長い処理を、経過時間だけで再起動しない。

意味的に不合格だった応答、拒否、上限打切りを成功が出るまで再生成しない。timeout後の請求・成功状態が不明な試行と、その後の再開は別attemptとして残す。SDK内蔵の隠れた再試行を無効化するか、全attemptを数えられるようにする。評価API呼び出し自体にはDB変更の権限を与えず、検査済み結果だけをホストが適用する。

実行前には各scriptの副作用を点検し、使い捨てcheckout・test DBで行う。最終検証中は編集しない。失敗が担当外のシステムに由来する場合は、証拠・影響・続行条件を報告し、そのシステムを勝手に修正しない。

### 共通のAPIキー設定

利用者が`~/.zprofile`に設定している`CLAUDE_API_KEY`と`OPEN_AI_API_KEY`を正本とする。プロジェクトごとの`.env`への転記は不要。今回、同じファイルの末尾に値を複製しない名前の対応付けを追加し、次の引継ぎを確認済み。

| 利用者の設定名 | SDKが使用する名前 |
| --- | --- |
| `CLAUDE_API_KEY` | `ANTHROPIC_API_KEY` |
| `OPEN_AI_API_KEY` | `OPENAI_API_KEY` |

SDK標準名が既に設定されている場合は、その値を優先して上書きしない。新規APIアダプターは標準名を読み、キーを文書・ログ・manifest・リポジトリへ保存しない。アカウントが異なる可能性のある`CODEX_API_KEY`を、直接OpenAI APIの実行へ暗黙に流用しない。

新しいログインシェルではこの対応付けを読み込める。既に開いているシェルは`source ~/.zprofile`で反映できる。GUIから起動したCodexなど、ログイン設定を読み込まない実行環境には、今回設置した共通ランチャー`~/.local/bin/with-api-keys`を使う。このランチャーは設定を読み込み、キーを引数にせず子プロセスの環境へ渡す。既存のCodexチャットへプロンプトを送る処理は含まない。

```sh
# 現時点でも使える既存の固定判断検証。API課金なし。
~/.local/bin/with-api-keys bun run check:memory --offline --suite all

# 以下はW3以降に新設するコマンド。現在は未実装。
~/.local/bin/with-api-keys bun run eval:memory:preflight -- --manifest <manifest>
~/.local/bin/with-api-keys bun run eval:memory:run -- --manifest <frozen-manifest>
```

確認済みなのはキーの有無、標準名との値の一致、子プロセスへの引継ぎである。キーの値は表示しておらず、APIの認証成功・課金・モデル権限はまだ確認していない。鍵がない状態ではoffline検証まで進め、live部分は未実行として明示する。

## 10. 保存する成果物と停止条件

各runのmanifestには、commit、source hash、case／正解／schema／prompt／採点器のhash、provider、モデル・返却情報、SDK/API版、effort、実行順seed、制限値、価格表と確認日を含める。各attemptには入力、原応答、request ID、結果分類、DB差分、根拠、時間、原usage、費用、失敗・再開関係を保存する。秘密値は含めない。

成果物は`verification-reports/quality-80/<run>/`へ置く。主なファイルは`manifest.json`、`calls.jsonl`、`state-checks.json`、`semantic-results.json`、`judge-disagreements.json`、`performance.json`、`cost-summary.json`、`summary.json`。source snapshotとartifact hashを対応させ、途中結果を成功結果で上書きしない。

同じ目的の試行を3ラウンド行った時点、または新しい証拠のない同一失敗、検証中の編集、計画逸脱を認めた時点で、次の編集・再実行の前に進め方を見直す。増えた証拠、減った残作業、未解決の仮説、続行または方針変更を現在の会話で短く報告する。同じ操作を再実行する場合は、前回と変えた条件を明示する。

80点未達時は、差分と検証結果を保持し、低い基準が実装不足・証拠不足・環境不足のどれかを示す。新しい根拠のない再試行や、検証対象を狭める加点は行わない。API budgetに達した場合は新規dispatchを停止し、完了数・未完了数・実費と不明額・再開条件を報告する。
