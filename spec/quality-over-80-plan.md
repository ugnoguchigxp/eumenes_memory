# Eumenes Memory 技術品質80点超えの改善計画

2026年11月16日。基準はローカル `main` の `00e9bc2`。技術品質 **65.3点**から、同じ基準で **80点を超える**ことを目指す。全項目の受入条件を満たした場合の試算は **82.5点**。最初に、障害復元で忘却済みの記憶が戻る問題を解消する。その後、並行更新、検索と回答、配布後の運用を検証して再評価する。

対象は SQLite コア、同梱 CLI・MCP、Eumenes への組み込み境界。作業中の予定管理は基準と採点から分け、DB移行とインターフェースの共存を別の結合試験で確認する。既存記憶の自動削除、外部サービスの運用変更、公開APIの契約変更はこの計画の実装範囲に含めない。

## 改善案と実施順

| 作業 | 範囲と改善案 | 受入条件 | 先行 |
| --- | --- | --- | --- |
| W0 基準固定 | 現行の採点、正常系の検証、復元・期限処理の再現、検索負荷を固定する。試験データ、期待値、環境、コマンド、計測予算を記録する。 | 使い捨てDBで、最新ジャーナルを失った復元と `use` と停止の競合を再現できる。ベンチの目的と条件を候補実装前に確定する。 | なし |
| W1 忘却を守る復元 | `backup.ts`、`transport.ts`。バックアップ内の最長の写しだけで復元の可否を決める処理を外す。独立保管された最新ジャーナルの確認、復元候補上での整合検査、DBの切り替えを分け、既存の所有者ロックと忘却再適用を使う。 | ジャーナルが欠損・短縮・破損・別系統の場合は既存DBを置き換えず停止。最新の写しで復元すると忘却済み項目は表示されない。切り替え前後の中断から、安全に再開できるか旧DBを維持できる。 | W0 |
| W2 期限と再試行の整合 | `expiry.ts`。停止を確定する writer transaction 内で、対象の revision、由来、最終利用日と期限を確認する。既存の操作IDと再試行処理を維持する。 | `use` が先に確定した項目は active を維持。停止が先なら利用側に有効な更新として返さない。再送、多重停止、訂正との競合で二重処理が起きない。 | W0 |
| W3 制限到達後の回復 | 既存の IPC、SQLite、checkpoint、モデル実行の制限を使い、再開の手順と状態表示を揃える。 | 同時要求、入出力上限、読み手による checkpoint 妨害、モデルの時間切れと取消を隔離環境で再現。失敗理由を区別でき、負荷や妨害を解いた後に処理が回復する。操作済みの結果は同じIDで照会できる。 | W0、W2 |
| W4 ホスト境界と配布 | CI、配布スクリプト、導入文書。README の版8表記を実装と揃え、SQLite 3.44以上・FTS5、コア版とホスト版、移行と復元手順を明記する。両配布物と依存・第三者表示を点検する。 | 配布物だけで保存、訂正、検索、忘却、復元が通る。版8→9、予定管理と共存する移行、Bun・Nodeのコア、CLI・新旧MCP、Eumenesのwriter連携を照合。欠落・改変した配布物は検査で落ち、macOS・Linuxの実CI結果を同じコミットで保存する。 | W1、W2 |
| W5 検索から回答まで | `natural.ts`、`meaning/retrieval.ts`、`search.ts`、既存の品質評価。全件取得を基準とし、既存FTSで許可済み候補を取得して共通の根拠評価を通す案を同じ質問で比較する。 | 1,001件の合成比較で、指示・スキーマを含む128 KiB内で根拠のある結果を返せる。対象範囲を網羅できない場合は、範囲の不足や上限を返す。根拠の取りこぼし、根拠のない断定、p95、費用を個別に記録し、事前に固定した採用条件を満たす。 | W0、W2 |
| W6 復旧演習と再評価 | 最終候補の配布物を使い、使い捨てDBで別環境から復旧演習を行う。基準と同じ30項目で採点し直す。 | 未解決の重大所見がなく、正式点が80点超。元の公開契約、権限、根拠、忘却に回帰がなく、検証結果が同一コミットの配布物に対応する。 | W1〜W5 |

着手は **W0 → W1**。W2 は基準固定後に独立して進められる。W1 はまず最新ジャーナルが確認できないときの自動復元を止め、次に復元候補を事前検証する。ジャーナルの連鎖が正しいことと、その写しが最新であることは個別に確認する。後者を既存機構だけで証明できる範囲を調べ、確証のない写しで復元を続けない。

W5 は、現行の `context`、`memory_search`、`recallSnapshot`、`Complete` と凍結済み比較器を再利用する。候補の意味選択と不足時の判断はモデルと共通指示に委ねる。コードでは許可ID・出典・応答サイズを検証する。短語や言い換えで候補を取りこぼす場合は、モデルによる再検索、または予算内の全件取得を比較する。特定の語句だけを通す処理や、黙って記憶を切り捨てる処理は採用しない。

## 性能と回答品質を測る条件

- SQLは既存の目標を引き継ぐ。1万件の検索 p95 20 ms、10万件の頻出語 p95 100 ms、本文編集の索引増分 p95 2 ms。短語・頻出語・混合語は別集計し、SQLiteのみとMCP経由を分ける。本文編集の増分を比べられる測定対照をW0で用意する。測れなければ未確認とする。 [検索ベンチマーク](search-bench-results.md)
- 自然文比較は合成1,001件の既存条件を再現し、言い換え、人物・時点の取り違え、訂正・忘却後、根拠が足りない質問を別枠で含める。候補の採用前に、根拠再現率・誤支持率の許容差と遅延・費用の上限を固定する。権限外の根拠、忘却済みの引用、不十分な範囲からの断定は固定試験で0件を要求する。構造化根拠の選択と自然文の最終回答は別に採点する。 [既存の容量評価](../examples/quality/RESULTS.md)
- 部分試験は合成データと固定モデル応答で実行できるようにする。結合では実SQLiteと隔離したEumenes fixture、通しではパック済みCLI・MCPを使う。最終候補で `bun run build:host`、`bun run verify:all`、`bun run verify:package`、`bun run verify:host` を実行し、実CI・依存確認・性能・復旧演習の記録を紐づける。実モデルの比較は試験条件と費用枠を固定した別工程で行い、利用を許可されたデータだけを使う。未実施なら、その試験を根拠とするアンカーは引き上げない。

## 合格判定と将来性

最終候補で **正式点が80点超**、適用基準の確認範囲が100%、未解決のCritical・Highと重大な未調査疑義がないことを合格条件にする。修正前に落ちる反例を修正後に通し、検証と採点の間に候補を更新した場合は影響を受ける試験を再実行する。差分から独自の意味判定、権限の緩和、他の作業の混入を点検する。

将来性は前回 **56.3点（暫定）**。技術改善の点数を転用しない。内部パイロットで、導入と復元にかかった作業、登録した記憶が実際に再利用された割合、訂正や見直しの手戻り、現行方式との回答品質の差、保守担当を記録する。次の継続・拡張判断では、この実利用の結果と、同じ課題を既存方式で処理した結果を比較する。
