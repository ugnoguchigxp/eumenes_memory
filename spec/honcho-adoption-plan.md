# Honchoの長所の採用とCLI MCP導入計画

作成日: 2026年11月7日。基準commit: `86fe3c9b95deffc090fb41a4ff77a0d8685e02da`。

Eumenes Memoryの出典・訂正・忘却の契約を維持し、Honchoから学べる人物の帰属、事実と推定の区別、根拠の追跡、導入経路を段階的に改善する。独自CLIとメモリーMCPを提供し、アプリと複数のコーディングエージェントが、許可された同じ記憶を継続して利用できるようにする。

本書は実装前に確定した計画を保存したものである。2026年11月7日の実装と受入の対応は[ホスト実装記録](host/implementation.md)を参照し、各検証の最終状態は検証レポートを正本とする。本体の現行契約は[全体設計](full-system-design.md)と[ホスト導入手順](../docs/host-guide.md)を正本とする。

## 1. 目的と完了条件

利用者がCLIで保存した記憶をコーディングエージェントがMCPから参照し、あるクライアントで訂正・忘却した内容が他のクライアントにも反映される。クライアント終了後も記憶は残り、忘却後に古いDBを復元しても、最新の忘却記録により再適用される。

完了条件は次のとおり。

- CLIとMCPを配布物から起動でき、同じホスト処理と公開Memory APIを使う。保存・訂正・忘却の別実装を持たない。
- CLIと独立した2つのMCPクライアントから、同じストアの保存・参照・訂正・忘却を通して確認する。再起動・競合・応答喪失後の再試行でも契約を維持する。
- 同じ操作IDで同じ操作を再試行しても重複適用せず、古い状態に対する計画は拒否する。拒否・一部失敗・確認待ちを成功へ読み替えない。
- 許可されないprincipalやscopeの記憶を読めず、要求にprincipalや保存先を書くだけで権限を広げられない。本人のscopeに保存された他人についての記憶（other_person_note）は、許可範囲なら参照できる。
- 推定由来の内容を本人確認済みとして扱わず、出典・条件・時点を保つ。記憶本文や引用中の指示を実行権限として扱わない。
- 部分、結合、配布物だけを使う通し検証を順に通過する。意味判断の変更は未使用の合成会話で現行方式と比較する。
- 実コーディングエージェントで接続を確認する。実Eumenesとの共有は、アプリ所有者側の接続と結合試験まで通って初めて完了とする。

計画の確定事項は、責任分担、基本操作の順序、権限と復元の不変条件、検証段階とする。P0で固定するwire schema、数値上限、SDK/runtime版、配布名は後述の成果物として管理し、未決定のまま実装段階へ進まない。接続対象の実エージェント名・版と実Eumenes側の担当・作業先もP0で記録する。

## 2. 対象範囲と再利用

本体は同期ライブラリのまま、接続・単一Writer・時計・モデル・アクセス認証・journal媒体をホストが所有する。CLIとMCPは、このリポジトリに追加するホスト側の入口とする。本体の非ゴールにあるHTTPサーバーやモデル呼び出しを、本体へ移管する計画ではない。

| 既存機構 | 再利用と必要な確認 |
| --- | --- |
| `examples/standalone/planning.ts` | 計画と実行の分離、訂正・共存・矛盾の判断、依存する変更のまとまり。意味判断を語句別の分岐へ置き換えない |
| `examples/standalone/execution.ts` | 操作ID、保存済み計画、再試行記録、古い計画の拒否。単一プロセス向けの前提を複数クライアントで検証する |
| `examples/standalone/host.ts` | DB・出典・journal・公開APIの接続を参考にする。例には固定principal/scope、追記式の出典ログ、forgetのplan/applyを別transactionで行う箇所があるため、そのまま製品化しない。ホスト導入手順の現行契約へ揃える |
| `examples/standalone/retrieval.ts` | 許可された記憶の入力、回答項目ごとの状態・根拠ID。提示した記憶と採用した根拠を区別する |
| `examples/standalone/model-input.ts` | 現在の入力は主体・値・期間等で、originは含まない。保存済みorigin等を提示する拡張を比較する。新しい記憶分類表は作らない |
| `examples/quality/` | 既存のモデル接続・予算管理・固定評価を検証に再利用する。モデル名や価格は実装時に確認し、過去の設定を無検証で固定しない |
| `eumenes-memory` と `eumenes-memory/sqlite` | State・Records・Temporal・忘却・変更フィードの公開API。CLI/MCPから内部テーブルを直接操作しない |

ホスト実装の配置案は`packages/host/`。その中に共通処理、独立起動、CLI、MCP、接続用クライアントを置く。本体と配布・依存を分離し、MCP SDK等の依存を本体へ追加しない。CLIとMCPは同じホスト配布物から別の入口として起動できる構成を基本とし、不要な複数パッケージやプラグイン基盤は作らない。パッケージ名・コマンド名は実装前に確定する。

製品のホスト層はexamplesを実行時依存にしない。必要な既存処理を最小限移し、examplesをその利用例へ置き換える。移動前後のfixtureと実SQLite試験で同じ契約を確認する。

共通化するのは、LLMへ渡す作業指示・情報の構成、提案のparser/validator、権限・出典の検査、実行と結果契約である。自然文CLIでは既存Completeが提案を生成し、MCPでは呼出し元エージェントが同じ提案契約に従う。呼出し元モデルを強制できないため、同じ意味判断結果になることは保証せず、同じ実行制約と結果形式になることを保証する。

## 3. 同じ記憶を共有する構成

```text
CLI ───────────────────┐
MCP接続用プロセス A ────┼─ 共通ホスト処理 ─ 公開Memory API ─ DBと忘却journal
MCP接続用プロセス B ────┘   ストアごとにWriterの所有者を1つにする
```

MCPクライアントごとの接続プロセスが、個別にDBとjournalを所有する構成は採用しない。DBのロックだけでなく、計画時の読み取り、適用前の照合、操作記録、journalの追記・fsync・適用までを同じ所有者が調整する。モデル待ちの間はDB transactionやWriterを保持せず、戻った計画は適用時に再検査する。

共通ホスト処理には、実際の利用形態に対応する2つの配置を設ける。

| 配置 | 所有者と接続 |
| --- | --- |
| 独立利用 | 専用プロセスがMemory用DB・journal・Writerを所有する。CLIと各MCP接続プロセスはローカルIPCで接続する |
| アプリ所有の記憶を共有 | アプリの既存WriterとDB接続を使うホスト処理へCLI/MCPを接続する。会話やアプリ側の消去と同じtransactionが必要な操作を維持する |

同じストアを独立プロセスとアプリが同時に所有しない。アプリ所有のDBをCLIが直接開く方式や、アプリDBから独立ストアへ黙ってコピーする方式は採用しない。実Eumenes側の接続実装は別リポジトリの作業として依存関係を記録する。

初期対応はmacOS/Linuxの同一OSユーザーによるローカル利用とする。IPCのソケットと設定をOS権限で保護し、接続先を利用者が管理するプロファイルで決める。ストア所有権の排他、同時起動、異常終了後の所有権回復を検証する。PIDの存在確認だけで所有権を判定しない。到達不能時に新しい空の記憶へ自動切替しない。

`init`と`serve`は明示操作とし、通常のCLI/MCPは既存の接続先へ接続する。自動起動や所有者の自動切替は初期範囲に入れない。所有者はDBとjournalの照合・必要なhostIntentの再適用を終えてからreadyを公開する。MCP接続プロセスの終了は、その接続だけを閉じ、共有所有者を終了させない。

アプリ配置のadapterは、アプリ所有のread snapshot、同期write transaction、出典参照、hostIntentの消去・再適用へ接続する。共通処理は渡されたtransaction内で公開Memory APIを呼び、内部で別connectionや入れ子transactionを作らない。アプリの既存書込み経路も同じWriter調整へ含め、IPC経由だけを直列化した状態を共有対応と呼ばない。

### 3.1 Snapshotと世代

ホストが返すsnapshotId・ページcursor・planId・出典を使う操作用handleは、対象ストア、起動世代、接続権限、policyRevision、対象scope、取得した版へ結び付ける。永続したitemIdやSourceRef自体を起動のたびに変更せず、操作用handleと永続参照を区別する。クライアントが送るhashやIDだけで整合性・権限を証明したことにしない。DB由来のseqは復元で巻き戻るため、世代をseqだけで表さない。所有者の起動ごとに新しい世代を発行する。

複数scope・複数ページを一つのsnapshotとして返す場合は、一回のread transactionで取得した有限の表示用データをホストが保持する。RPCをまたいでDB transactionを保持しない。ページ上限には同じsnapshot内のcursorを返す。snapshot全体の容量上限を超える場合は取得範囲と未完了を返し、提供できない続きのcursorを発行しない。cursorの期限切れ、起動世代の変更、権限変更では新規snapshotを要求する。

適用とモデル結果の返却前には、対象scopeの変更フィードだけでなく、今回参照するホスト所有の出典状態・依存関係・アクセス方針の変更も照合する。context取得後に新しく登録した出典は、その参照と版を提案へ追加して検査する。別の未参照出典の追加だけではsnapshotを失効させない。照合から結果確定までを所有者が順序付ける。参照範囲に変化があればstaleとして返し、モデルの自動再生成を繰り返さない。関係ないscopeの更新だけを理由に全クライアントの計画を失効させない。

共有されるのは記憶サービスとストアであり、コーディングエージェントの現在の会話や思考状態ではない。既存チャットへの送信、他エージェントの自動操作、利用者設定の自動書換えは導入に含めない。

## 4. アクセスと記憶の種類

初期構成は同じ本人を単一principalとして扱う。アプリやエージェントの識別子は操作元の記録に使い、別の本人を表すprincipalと混同しない。既存本体の単一principalでの検証範囲を、マルチテナント保証へ読み替えない。

- プロファイルに、保存先、許可scope、読取・書込・忘却の権限、モデル利用と予算の設定を持たせる。ツール引数からこれらを上書きできないようにする。
- プロジェクト内の記憶と、本人が共有を選んだ好み等をscopeで分ける。別プロジェクトへ自動公開しない。scopeの候補を選ぶLLMの判断と、scopeへのアクセス許可を分ける。
- プロジェクトとの対応はホスト設定が管理する。要求内のパスやリポジトリ名だけを信頼して、既存プロジェクトの権限を付与しない。
- 保存元の話者・出典・revisionと保存時のoriginを保持する。既存クライアントの推定を、別のエージェントが読んだだけで本人確認済みへ昇格させない。
- コーディングエージェントが扱うプロジェクトの任意情報を、本人のpersonal_fact等へ無理に分類しない。初期対象は既存契約に収まる記憶とRecordsとし、案件・意思決定・Rule/Skillの正本移管は別設計とする。

記憶の取得・更新を選ぶ意味判断は呼出し元のLLMまたは既存Complete接続が担う。コードは許可されたID、出典、版、操作形、件数・長さ・予算を検査する。記憶の内容を実行ポリシーや指示として自動採用しない。

接続権限は、所有者が管理するローカル認証情報で各CLI/MCP接続へ付与する。接続時に確定した権限を各操作で再検査し、client名・任意のprofile名・ツール注釈を認証情報として使わない。認証情報をLLMへの入力に含めない。この制限はサービスを通る操作に対するもので、同じOSユーザーの権限でDB・設定・認証情報を直接読める悪意あるプロセスとの隔離を保証しない。

本体のCASは値の版の一致を検査するもので、推定が本人確認済みの値を置き換えることを一律には禁止しない。製品ホストでは、本人確認済みの項目の訂正・停止解除・削除を行う権限を別に検査する。新しい推定や取得結果だけではその権限を付与せず、権限不足は対象を変更せず返す。曖昧な対象の選択はLLMが確認に回し、コードは特定語句から訂正意思を認定しない。

### 4.1 忘却がscopeを越える場合

本体の`planForget`と`getForgetReceipt`は、対象scopeの確認後、同じprincipalの依存閉包全体の件数や外部IDを返しうる。公開APIには全閉包のscopeを列挙する契約がないため、その応答をscope限定のクライアントへそのまま公開しない。

初期版の忘却は、当該principalの全scopeを管理する権限を持つ接続だけに許可する。scope限定接続からのforget計画・適用・receipt読取は、本文・件数・IDを返す前に拒否する。閉包を権限のある部分だけへ切り詰めて成功にしない。将来scope限定の忘却を許可する場合は、公開APIまたは検証可能なホスト情報だけで全影響範囲を確認できる契約が前提となる。

通常の操作結果・計画・出典も、作成時の権限だけでなく照会時の権限で検査する。権限を失ったクライアントが、古いplanIdやoperationIdから内容を取得できないようにする。

## 5. CLIの機能案

コマンド表記は仮の`eumenes-memory`とする。表示用の短い結果と、機械から使うJSON出力を用意する。未実装のコマンドを現在のREADMEの導入手順へ掲載しない。

| コマンド案 | 役割 |
| --- | --- |
| `init` / `status` | 明示した新規ストアの初期化、接続先・schema・復元照合・未完了操作の確認。本文や秘密を診断ログへ出さない |
| `serve` | 独立ホストの起動・終了。共有ストアの所有権を保持する |
| `source` | 明示して渡された発話等をホスト出典として登録し、提案で使う参照を取得する。保存済みのアプリ出典はadapterで解決する |
| `context` / `read` | 許可された記憶のsnapshot・ページと、指定IDの詳細・出典を取得する |
| `plan` | 既存の自然文計画、または呼出し元LLMの構造化提案を検査して計画IDを返す。この段階では記憶を変更しない |
| `apply` / `operation` | 保存済み計画を操作IDで適用し、同じIDから結果確認・再開する |
| `recall` | 既存のモデル接続で質問ごとの根拠を取得する。モデルを使う条件と費用の設定を明示する |
| `forget plan` / `forget apply` | 対象と範囲を提示し、共通の計画・適用経路で忘却する |
| `mcp` | stdioのMCP接続プロセスを起動し、同じホスト処理へ接続する |

JSON出力は状態・reasonCode・operationId・根拠ID等を安定した契約で返す。終了コードは正常完了、要確認、一部失敗、接続/契約エラーを区別する。部分成功でも全件成功の終了コードにしない。コマンド名の振分けと入力形式の検査以外に、発話やキーワードによる意味分類を追加しない。

状態の意味は、読取/出典登録成功、適用可能な計画、全適用完了、要確認、部分適用、適用前の拒否、実行失敗、結果不明を区別する。正常なplanの終了は記憶の更新完了を意味しない。CLIの非ゼロ終了だけで未適用と推定せず、operationIdと保存済み結果を正本にする。MCPのprotocol error、tool実行エラー、業務上の要確認等への対応はP0の状態対応表で固定する。

モデル不要のcontext/read/構造化plan/applyを提供する。自然文plan/recallでは既存Completeを再利用し、別の計画器を作らない。秘密情報の設定はホスト側で管理し、CLI引数・MCP結果・通常ログへ複製しない。

## 6. メモリーMCPの機能案

初期transportはローカルのstdioとする。公式TypeScript SDKを用い、外部公開HTTPと認証サーバーは初期範囲に含めない。SDKと対象クライアントの対応プロトコル版を実装前に確認して固定し、旧版との接続互換を試験する。

| ツール案 | 役割と境界 |
| --- | --- |
| `memory_source` | 明示して渡されたテキストの出典を登録し、ホストが発行する参照を返す。本文登録と事実の採用を区別する |
| `memory_context` | 許可scopeの記憶をorigin・主体・時点・revisionとともに渡す。snapshot識別子、取得範囲、続きの有無を明示する |
| `memory_read` | 許可IDの詳細・出典を取得する。取得範囲外のIDから別scopeへ到達させない |
| `memory_plan` | 呼出し元LLMが作った保存・訂正・忘却の提案を共通validatorで検査する。ホストが発行したsnapshot・出典参照へ結び付け、計画IDを返す |
| `memory_apply` | 計画IDと操作IDを受け、最新状態・実行権限を再検査して適用する。古い計画なら再計画を求める |
| `memory_operation` | 応答喪失・再接続後も操作IDで実際の保存済み結果と再開可能性を確認する |
| `memory_status` | 接続・schema・復元照合・未完了の外部削除等を、許可された範囲で返す |

ツール名とschemaは契約策定時に確定する。MCPによる基本利用では、呼出し元のコーディングエージェントが意味判断を行い、MCP内部の追加LLM呼び出しやAPIキーを必須にしない。CLIの自然文経路と同じ出力契約・検査・適用処理を使う。

初期contextの列挙対象は既存APIで取得できるStateとする。外部資料のRecordsは、source登録またはStateの根拠から得た参照でreadできるようにする。任意のRecordsを全文検索・全件列挙する機能は、このツール名から暗黙に約束しない。情報不足でプロジェクトの任意事実をStateへ押し込むことも認めない。

新規保存の基本手順は、context取得→source登録→呼出し元LLMの提案→plan検査→apply→operation照会とする。提案は、構造化された変更・根拠の出典参照・引用範囲・関係する既存ID・依存する変更のまとまりを持つ。引用範囲はUTF-8 byteで扱い、本文・revision・digest・scopeはホストの登録内容から解決する。planはState/Recordsの採用や忘却を実行しないが、期限付きの計画metadataを保存できる。取得だけならcontext/readで終える。各段階の拒否を飛ばしてapplyしない。

保存だけの依存グループは原子的に適用し、忘却だけのグループは耐久記録した意図から再開可能にする。保存と忘却が一体で成功しなければならない混在グループは初期版では未対応として要確認にし、独立した操作へ黙って分割しない。本体の1回のtarget上限を超える忘却は、最初のentryのhostIntentへ全対象の不透明なIDを載せ、DB復元後にも残る意図として記録してから、上限内のentryへ分割して再開する。対象全体がhostIntentの上限を超える場合は、変更前に拒否する。全entryと必要な外部消去の完了前にグループ完了と表示しない。

MCPが返す情報には、呼出し元LLMが提案契約を理解するための版付きの作業指示と、通常の記憶データを区別して載せる。安定したツール説明・信頼規則を記憶本文から生成しない。LLMに原文の同義性を判断させる範囲と、ホストが機械的に拒否する条件を明記する。

取得では、モデルへ提示された記憶と、回答根拠として選ばれた記憶を区別する。全件取得していない応答を「完全な記憶」と表示せず、記憶が見つからない状態と未取得・契約違反・通信失敗を分ける。質問に応じた候補取得の追加は第8節の比較後に判断する。

広い意味範囲の事実を全て選ぶ提案では、該当scopeの取得が完了していることを前提にする。部分取得しかできない場合は、その範囲を明示した操作へ狭めるか要確認とし、「全て忘れた」と返さない。明示した出典IDの忘却や、指定itemの履歴展開は既存の構造的な依存処理で行う。

MCPのJSON-RPC要求IDを、再試行可能な操作IDとして流用しない。取消や接続断の前に保存が完了していた場合は、失敗を理由に取り消したと推定せず、操作記録から状態を確認する。journal追記後の忘却は未完了として保持し、接続断を理由に捨てない。

stdioのstdoutはMCPメッセージだけにし、診断はstderrへ出す。toolの説明やread-only等の注釈だけで権限を強制せず、共通ホスト処理でも検査する。確認が必要かどうかは付与済み権限・ユーザー依頼・クライアント側の運用に従い、plan/applyの分離自体を毎回の人手承認要件にはしない。

## 7. 出典と忘却を共有経路で守る

1. ホストが登録した出典参照と、LLMが提案した内容・引用を分ける。ホスト所有の原文・話者・revision・digestから既存EvidenceSpan検査へ接続し、モデルが任意の発話を本人確認済み出典として発行できないようにする。MCP経由の提案は原則agent_inferredとし、信頼するホストが本人の確認操作と出典を検証できる場合だけuser_confirmed/user_editedを許す。CLIから呼ばれたこと自体を本人確認の証拠にしない。
2. 計画保存や操作記録が、忘れた本文の隠れた複製にならないようにする。本文を持つホストの保存物は、必要な依存・hostIntentと保持期限を設計し、忘却時に除去する。記録をIDとhash中心にできる場合は原文を重複保存しない。
3. plan・journal追記とfsync・applyは既存契約どおりWriter内で調整する。ホスト自身が所有する原文や派生物の消去も、同じtransactionとhostIntentの再適用へ接続する。
4. 外部依存・キャッシュ・計画の未適用結果も、変更フィードとrevisionで失効させる。モデル待ちの間に今回参照した記憶・出典の版が変わった場合は第3.1節の照合を行い、古い結果を新しい記憶の回答として返さない。忘却後に古いキャッシュや計画から再保存しない。復元時は再登録とfeed再同期を含めて検証する。
5. 初期化、再起動、古いDB復元、journal欠落・破損を区別する。既存データでjournalが見つからない場合に空のjournalを自動生成しない。

### 7.1 出典登録と忘却の範囲

`source`は明示的に受け取ったテキストだけを登録する。会話履歴やローカルファイルを自動収集しない。出典は、アプリ所有の既存発話、クライアント提出テキスト、外部資料を区別し、提出者の自己申告だけで話者や本人確認を認証しない。会話の正本はホストに置き、Recordsを会話原文の置き場へ転用しない。外部資料の本文保持はRecordsの既存契約で扱う。

登録はsubmissionIdで冪等にし、同じIDの異なる本文を拒否する。長い出典は本体の上限内で受け、Stateの根拠には`LIMITS_STATE`内の引用範囲を選ぶ。従来例の「発話全文をquoteにする」制約を製品経路の必須条件にしない。同じ引用文が複数回ある場合も、指定されたbyte範囲で識別し、語句を補正して別の引用へ置き換えない。

クライアント提出テキストはホスト所有の出典へ登録し、外部資料はRecordsへ登録する。いずれもsource登録時点で本文は保存されるが、人物についてのStateを採用したことにはならない。sourceを変える操作にも書込権限と容量制限を適用する。新しい外部資料をsourceとして保存することと、planが読取専用であることを混同しない。

出典・計画の未採用データには容量と有効期限を設ける。採用したStateが参照する出典を期限だけで破棄せず、依存を先に確認する。出典の期限切れ・版変更・忘却では計画を拒否し、古いテキストを新しい出典IDへ付け直して再試行しない。

忘却計画は、Stateの全版と登録派生物を消す操作、元の出典とその全派生物を消す操作を区別し、原文まで対象かを返す。Stateだけを忘れる操作は、元の発話まで消したと表示しない。元の発話からの再抽出も止める要求なら、ホスト出典と関連する計画・保持物の消去/再利用禁止まで含める。忘却済みの出典参照とsubmissionIdを新規登録として再生しない。

一つの原文に、忘れる事実と保持すべき事実が含まれる場合、原文を丸ごと消すことで保持条件を破らない。既存契約で両立できない部分は要確認にして保留し、独立した変更だけを進める。文字列置換で原文を改ざんしたり、Stateだけ消して原文まで消去済みと表示したりしない。物理媒体・バックアップ・既にクライアントへ渡した複製への保証は、ホスト導入手順と同じ範囲に限定する。

### 7.2 操作記録と復元

操作はクライアントが指定するoperationIdと、ホストが保持する版付きの計画内容へ結び付ける。クライアントはIDと受付対象の起動世代をapply前に保持し、applyとoperation照会で送る。最初のapplyで対応を永続化し、同じIDで異なる計画を適用しない。保存グループの変更と結果記録を同じtransactionでcommitする。忘却はjournalへ耐久記録した意図を正本に、ローカル適用と外部削除の状態を追跡する。外部削除がpending/unverified/failedなら全体完了を返さない。

忘却のhostIntentには、ホスト所有の出典・提出IDの再利用禁止・実行payload等を消去するための不透明なIDを含める。起動時はその意図を本文なしで再適用し、ホスト用の墓標も復元する。DBだけを戻した場合に消去と再利用禁止が失われないことを確認する。既にjournalへ受理した消去意図は所有者が回復処理として完遂し、元クライアントの切断や権限失効を理由に破棄しない。クライアントへの結果公開には現在の権限を適用する。

再試行では、まず現在の権限と既存の操作記録を確認する。確定した同一操作は保存済み結果を返し、未完了操作は検証した記録から再開する。この照会を古いsnapshot検査より先に行い、自分の適用結果でsnapshotが変わったことを理由に、適用済み操作を不明扱いしない。新しい操作や変更された計画には最新状態の検査を適用する。

通常の再起動では、保存済み計画を検査可能な操作の再開に使えるが、未着手計画やcursorは新しい起動世代で失効する。古いDBを復元すると、バックアップ後の操作記録そのものが失われうる。最新journalによる忘却再適用と、一般の保存操作の完全な履歴回復は別である。記録が見つからない旧世代の操作は結果不明として返し、自動で再適用しない。新しいsnapshotを取得し、実際の状態を確認してから新しい操作として計画する。

受理済み操作の実行用payloadには、検査済みの永続参照・版と変更内容を保持し、接続中だけ有効なhandleを再開条件にしない。所有者は再起動後も出典と現在状態を再検査して再開し、payload消去や版の不一致があれば実行せず状態を返す。未着手の古いplanをこの回復経路へ流用しない。

結果照会に必要なID・状態は保持方針を決め、本文を含む実行用payloadと分離する。forgetでpayloadを消しても完了済み操作の再実行を許さず、削除後の結果照会から忘れた本文を返さない。同じ起動世代の間は、詳細記録の期限後も使用済みoperationIdと対応する計画の識別情報を保持し、再送を新規操作として受け付けない。旧世代で詳細記録も残っていない操作は結果不明とする。保持上限に達した場合は新規操作を拒否し、重複検出の記録を無言で捨てない。

製品の通常ログはID・状態・時間・usage中心とし、入力原文やモデルの生応答を既定で複製しない。診断で本文を保持する機能を設ける場合は、その保存先も出典・依存・保持期限・忘却の管理対象にする。忘却で失効した進行中のモデル応答を、新しいログや計画として保存し直さない。

既にクライアントへ渡した本文や、そのクライアントの会話履歴はMCPサーバーだけでは消去できない。保証対象はホストが管理する保存物と忘却後の新しい読取・適用であり、クライアント所有の履歴消去は連携先の責任として区別する。

## 8. Honchoから採り入れる改善と採用判定

| 改善候補 | 最初の比較と採用条件 |
| --- | --- |
| origin・話者・時点の提示 | 既存情報をLLMに渡す変更だけを先に比較する。本人/他人の誤帰属、推定の断定、時点の混同が減り、既存の訂正・忘却を壊さないこと |
| 根拠を追跡できる回答 | 入力snapshot、選択された記憶、元の出典を既存IDで接続する。取得された全資料を回答の裏付けと誤表示しないこと |
| 複数発話からの事実抽出 | 話者・時刻・引用元を渡し、既存計画指示で独立した主張を抽出する。会話原文の正本を本体へ移さず、保存のoriginを正しく保つこと |
| 大量記憶の候補取得 | 全件入力を基準に、本文長・件数・費用・p95・取りこぼしを比較する。既存の候補取得実験を再利用し、改善が確認できた条件に限って導入する |
| 記憶の整理・人物モデル | 本体のStateへ推測を事実として上書きしない。World/Consolidationは現行どおり別領域で設計し、必要なら変更フィードとExternalDependentで接続する |

共通の通し評価では、未使用の合成日本語会話、正解・許容根拠・採用条件、ソース・モデル・指示・費用上限を実行前に固定する。全会話を直接モデルに渡す方式も対照とし、保存済みの正しい事実を与える段階別評価と区別する。各候補の悪化と失敗応答を残す。

### 9.1 P0の成果物と実装開始条件

P0は調査と契約策定の段階とし、次の内容を版付きの契約資料と対応するケース一覧へ保存する。成果物が未完ならP1以降へ進まず、不足する根拠・決定者・再開条件を記録する。

- source、context、提案、plan、apply、operationの入出力schema。CLIの終了コード、MCPのエラー、共通の業務状態の対応表。新規・同値・訂正・共存・矛盾・忘却の操作例と、無効な入力の拒否条件。
- ローカル認証情報の発行・保管・失効、プロファイルと実ストアの対応、全scope管理権限と限定接続の違い。出典の話者・originを認定できる経路と、その権限を持たない通常MCP経路。
- ホスト所有のsource・plan・操作記録・墓標の永続先と版。snapshot/cursorの寿命、操作記録と実行payloadの分離、バックアップ復元時の世代変更とhostIntentによる回復。
- 1要求/応答のbyte数、引用と提案数、同時接続/待ち要求/モデル実行数、snapshotの容量とTTL、未採用出典・計画・操作記録の保持期限、接続とモデルのtimeout、モデルの入力/出力/費用上限。既存LIMITSに収め、超過時の状態と検証値を定める。
- SDK/runtime/対応プロトコルと実クライアントの版、パッケージと起動名、初期化→所有者起動→CLI/MCP接続の手順。実Eumenes側のadapterに必要な変更先・担当・受入試験。意味改善の比較指標・採用閾値とAPI予算。

### 9.2 実装時に満たす境界ケース

以下は将来の実装試験の受入条件であり、本書のレビューで動作確認済みの結果ではない。通常の保存・読取に加え、各ケースの状態・出力・DB差分・journalを確認する。

| ID | 条件 | 期待する観測結果と禁止する挙動 |
| --- | --- | --- |
| R01 | 空の記憶に新しい発話を保存する | source→提案→plan→applyが進み、別MCP clientでStateとoriginを読める。未発行の出典IDでは保存されない |
| R02 | 同じ引用が繰り返される長文と、同じsubmissionIdの再送 | byte範囲で引用を検査する。同じ内容は同じ登録結果、異なる内容は拒否。全文quote制約や自動補正で失敗を隠さない |
| R03 | 推定を本人確認済みの訂正として提案する | user由来へ昇格せず、必要な権限がなければ既存の本人確認済み項目を変更しない。参照結果だけを本人の明示指示と認定しない |
| R04 | 不許可scopeのID、別接続の計画/操作ID、権限失効後の照会 | 現在の権限で検査し、本文・件数・外部IDを漏らさない。profile名やclaimed principalで権限が変わらない |
| R05 | 許可scopeの出典に、不許可scopeの依存がある | 限定接続ではforget計画・適用・receiptが事前拒否される。全scope管理接続では完全な閉包へ適用する。閉包の切詰めはしない |
| R06 | 他人に関する記憶、部分snapshot、ページ期限切れ | 許可scopeのother_person_noteは参照可能。部分取得を全件と表示せず、全意味範囲の忘却に使わない。期限切れcursorは拒否 |
| R07 | 同時更新、モデル待ち中の忘却、無関係scopeの更新 | 同じ項目への一方の訂正はstaleになる。忘却済みの入力による回答を新しい結果として返さない。無関係な更新だけでは拒否しない |
| R08 | applyの成功応答だけが失われ、同じ操作を再送する | 保存済み結果を返して変更/履歴を増やさない。別計画で同じ操作IDを使うと拒否。詳細記録の期限後も重複適用しない。MCP要求IDを変更しても同じ操作を照会できる |
| R09 | journal追記後に終了し、元クライアントの権限も失効する | 所有者の起動時回復で消去とホスト墓標を再適用する。元クライアントへは不許可の結果を出さず、受理済み消去を放棄しない |
| R10 | 古いDBを復元し、最新journalと旧操作IDを使う | 忘却を再適用する。消えた一般操作記録を未実行と決め付けず結果不明にする。旧snapshot/未着手planから保存を再生しない |
| R11 | 一つの原文の部分忘却、上限を超える履歴、未完了の外部削除、古いpayload | 保持条件と両立しない原文消去や依存する保存/忘却の混在グループは要確認。分割したentryを再開し、Stateだけの消去と原文消去を区別する。途中状態や外部pending等を全体完了と表示しない。削除済みpayloadから本文や操作が復活しない |
| R12 | MCP接続終了、共有所有者の停止、ログ出力 | 接続終了だけでは他clientを止めない。所有者停止時は接続エラーとなり空ストアを作らない。stdoutにはMCPメッセージだけを出す |
| R13 | 記憶本文が指示変更を要求する、情報不足、同じ失敗の反復 | 本文をデータとして扱い、権限・指示を昇格しない。未知・要確認・実行エラーを区別し、設定上限を超えて再生成/再試行しない |
| R14 | アプリが自分のtransaction内で保存/忘却し、同時にMCPから更新する | 全経路が同じWriterで調整され、入れ子transactionや別connectionへの分離がない。アプリ側の原文消去も復元後に再適用される |

意味改善の採否では、事前固定した安全性ケースに新しい誤帰属・未根拠断言・誤忘却を生じないことを必須とする。品質・費用・遅延の比較閾値は結果を見る前に固定する。満たさない候補は採用せず、失敗を許容するために正解や範囲を変更しない。

## 10. 変更境界と戻し方

この計画の初期実装では、本体のDB schema・公開APIを変更せず、ホスト側の追加で成立するかを先に確認する。主な変更先はホスト用パッケージ、examplesの接続、ホスト試験、ビルド/配布/CI、導入手順とする。既存の記憶ファイル、資格情報、接続設定には自動適用しない。

本体契約で満たせない具体的な失敗が見つかった場合は、再現条件と最小の契約変更を設計へ追記してから実装する。既存APIと型の変更、本体への依存追加、モデルの自動切替、別principal間の共有、Windows対応、公開HTTP、任意SQL・shell・ファイル操作ツールは初期範囲に含めない。

戻すときはCLI/MCPの接続を停止し、既存ホストの利用へ戻せる配布境界を保つ。ただし、一度適用した忘却や進んだschema/journalを旧版へ巻き戻さない。新しいホストmetadataの変更は版管理し、ロールバック可能な範囲を配布前に試験する。
