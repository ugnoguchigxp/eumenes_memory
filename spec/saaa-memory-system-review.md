## 1. 結論

SAAA は「過去の会話を検索する機能」より広い。原文から状態を抽出し、出典と依存関係を保存し、訂正・忘却・権限変更を反映し、その時点で使える情報を会話へ渡し、回答を採用する直前にも有効性を確認する仕組みである。

この一連の契約が最大の採用価値。Records、ベクトル検索、プロフィール抽出をそれぞれ別機能として移植すると、後で正本と削除責任が分裂する。**MemorySystem を一つの論理的なシステムとして設計し、機能単位で有効化する構想を推奨する。**

独立リポジトリ化にも妥当性がある。すでに `personal-state-core` という IO を持たない Rust コアが存在する。ただし現在の MemorySystem 全体は SAAA の DB、ジョブ管理、実行状態、アプリの起動終了、モデル接続に結び付いている。今すぐフォルダを移せば汎用ライブラリになる状態ではない。リポジトリの分離と別プロセス・別 DB・リモートサービス化は別判断とする。

## 3. システムを構成する層

| 層 | 現在の役割・評価 | Eumenes に残したい性質 |
|---|---|---|
| Source / Evidence | 会話原文の版・範囲・ハッシュ・利用可能性を管理。Records は外部取得物を保持する | 原文所有者を保った参照、出典の追跡、取得物と主張の区別 |
| Personal State Core | Objective、Constraint、Decision、OpenLoop、Preference、PersonalFact 等を扱う決定的なコア | 候補と採用状態の区別、版競合、原子的な変更、再実行、間接依存の失効 |
| Extraction / Admission | モデルからの候補を厳密な形式・引用・スコープで検査して採用する | モデルに権限や採用結果を決めさせない。曖昧な推論を確定情報に昇格させない |
| Projection / Context | 必要な現在状態と履歴を予算内に組み立てる。未処理の新しい原文も考慮する | 古い要約を最新の事実として扱わない。不足・未処理・超過を明示する |
| Recall / Records | 検索・範囲読み出し・ページング・本文保存を提供する | 検索候補は根拠候補。検索ヒットや保存成功を、そのまま真実の採用としない |
| World | エンティティ・関係・焦点・条件・予測・観測結果を扱う。台帳から投影する | グラフを第二の正本にしない。予測、観測、因果の主張を区別する |
| Retrospective / Consolidation | 過去の範囲を固定した manifest、処理位置、採用条件を伴う再評価 | 同じ材料を何度も要約して確信を増やさない。進捗と入力を再現可能にする |
| Lifecycle | 訂正、忘却、スコープ変更、再起動、復元に伴う状態変更 | 原文から派生物・利用中の回答まで失効を伝える |
| Runtime / Provider 接続 | ジョブの claim、実行中断、LARM/local 接続、回答採用、アプリ起動終了 | Memory 固有の判断とホストの実行管理を分ける |

分類は本評価の整理であり、現行ディレクトリと完全に一対一ではない。特に World の実行時フレームと外部モデル接続は、独立コアよりホストアダプターに属する。[E02–E09]

## 4. 実際につながっている処理

現行の主経路は `runtime/conversation_check/queue_runtime.rs` → `queue_context.rs`。旧 runtime の削除や一部の `cfg(test)` を根拠に「Memory が使われていない」とは判断できない。

1. ホストが確定した会話原文を保存する。Personal State 側では原文の版・処理対象・失効に関係する状態を追跡する。
2. ワーカーが処理対象を取得する。原文と関連状態は範囲を絞ってモデルへ渡し、形式と出典を検査した候補を作る。
3. モデル呼び出しの後、ジョブ、原文、スコープ、キャンセル状態を再確認し、変更と進捗をトランザクションで確定する。
4. 会話開始時に履歴と Personal State を投影する。メモリー有効時は競合する旧 memory_items を除き、必要に応じて World を加える。
5. 結果の採用前と DB への確定時に、原文・スコープ・投影の stamp・World の根拠を再検証する。

メモリーの有効状態は保存された設定と環境の指定に依存する。「常に ON」「常に OFF」とは評価しない。アプリ初期化から worker の起動は確認したが、今回の調査で実モデルによる会話は動かしていない。[E04–E05]

## 5. 維持する価値が高い設計

**決定的なコアがすでにある。** `personal-state-core` はモデル・DB・時計・ID 生成を内包しない。ホストが入力を与え、コアが妥当な遷移か判断する。この境界は独立リポジトリ化の出発点になる。今回、リポジトリ指定の検証ラッパーで当該パッケージのテストが通った。[E02–E03]

**忘却は引用箇所だけの削除ではない。** 引用されなかった入力も含め、派生情報の依存閉包を無効化する考え方がある。古い推論が別表現で残る問題を扱ううえで重要。外部プロバイダーでの完全な消去まで今回確認したわけではない。[E02、E10]

**回答に渡した後にも確認する。** 検索時に正しかった情報でも、生成中の訂正・削除・スコープ変更で使えなくなる。投影の取得と回答の採用を結ぶ検証は、単純な検索ストアより先に移植すべき性質である。[E04]

**自動抽出に採用条件がある。** 出典引用、明示・推論・引用文の区別、プロフィールの競合、入力の新旧を扱う。もっとも、引用が一致することと意味が正しいことは別であり、日本語での意味評価を省略する根拠にはならない。[E05、E10]

**World を派生ビューとして扱っている。** 関係グラフのために第二の真実を作らず、同じ出典・主張の履歴へ戻れる方向は維持したい。ホストの実行状況を表すフレームは分離して扱う。[E09]

## 6. 移植判断に関係する課題

### F01 — 再利用したい処理にホスト固有の責任が残る

Medium / P1 / 信頼度 Medium。対象は `personal_state/worker.rs`、`jobs/claim.rs`、`product_binding.rs`、`worker_run.rs` と現行会話経路。[E04–E05]

- 条件: MemorySystem を Eumenes や独立パッケージから利用する。
- 結果: ジョブ管理、SAAA の runtime テーブル、Tauri の起動終了、LARM の接続・資格情報が関係し、一つのアダプターを交換するだけでは利用できない。
- 反証確認: IO のないコアは独立している。問題は「全体が分離不可能」ではなく、周辺の所有関係が未整理な点。
- 対応: 原文、保存トランザクション、ジョブ、推論、回答採用のホスト側ポートを定める。Eumenes に二つ目のスケジューラーを持ち込まない。
- 受入: Tauri・LARM・SAAA 専用テーブルなしで共通契約テストが動き、実アダプターは既存の writer と queue を使う。

### F02 — 前景の Personal State 読み出しが全履歴に依存する

Medium / P2 / 信頼度 Medium。`store.rs:16` は全 source refs、台帳、遷移等をロードし、`snapshots.rs:114` の view はこの処理と全 snapshot 行の読み出しを使う。会話の組み立て・採用確認から到達する。[E04、E06]

- 条件: 長期間の利用で、現在の会話と無関係なスコープを含む履歴が増える。
- 結果: 一つのスコープを見る処理が無関係な履歴の件数にも依存する。原文ごとの照会も発生する。
- 反証確認: `load_world_query` には根と必要な依存閉包に絞る実装がある。全検索経路の問題ではない。今回、実測で応答時間の悪化を確認したわけでもない。
- 対応: 対象スコープの根と必要な依存だけを読む。採用時には軽量な版・有効性の検査を使い、全履歴の再構成を避ける。
- 受入: 同じ出典・失効結果を保ち、1千・1万・10万件、複数スコープで読む行数、メモリー量、p50/p95 を比較する。閾値は Eumenes の応答予算から定める。

### F03 — Records の忘却がバックアップ復元をまたいで完結しない

Medium / P1 / 信頼度 High。`personal_state/journal.rs:61–99`、`records/auth.rs:26`、`records/schema.rs:98`、`records/forget.rs`。[E07–E08]

- 条件: 忘却前の record 行がある DB を復元し、外部 journal の record tombstone を再適用する。
- 結果: journal の再適用は tombstone を挿入するだけで、既存の `records.forget_epoch` を更新しない。読み出しの認可条件は tombstone を直接参照しないため、この既存行は読み出し対象に残る。さらに通常の journal 同期は personal/schedule tombstones だけを集め、record tombstones を保存しない。
- 確認: 実際の records スキーマと認可 SQL を取り出した独立 SQLite 検証で再現。通常どおり `forget_epoch` を更新すると非表示になることも確認した。
- 反証確認: 通常の忘却は非表示化と派生保存物の削除を行う。挿入トリガーは忘却済み ID の新規作成を拒否する。しかし復元済みの行は挿入トリガーを通らない。既存テスト `cw_51` は墓標の存在を確認するが、復元済み行の不可視性を確認しない。
- 対応: record の墓標を journal に永続化し、復元後の読み出し開始前に本来の失効処理を再適用する。認可条件にも墓標除外を加え、派生物・FTS・blob を検証する。
- 受入: 実 capture → 忘却 → 再起動 → 古い DB と最新 journal による復元で、read/search/派生 view に出ない。再適用が冪等。journal 欠落・破損時には復元データを利用しない。

これは SQL 部品とソース追跡で確認した復元契約の欠落であり、本番環境での情報露出や完全な Tauri 復元手順を実証したという意味ではない。SAAA 本体の修正は今回行っていない。

## 7. 既存の検証記録から言える範囲

Personal State の過去の成果物には、オフラインの契約テストと未完の製品接続・実モデル評価が区別されている。日本語 gold の人手確認や、外部接続先の忘却後不在確認に未確認項目が残る時点の記録がある。

World にも fixture の route 検証と性能測定がある。一方、それは今回の Personal State 前景読み出しと同一条件ではない。10月1日の記録にも実モデル受入を再実行していない旨がある。**過去の未達を現在の障害と断定せず、現在の成功証明としても使わない。**[E10]
