# メモリー単体の動作チェック

Eumenes を起動せず、公開 API と実 SQLite ファイルを使って動作を確認する小さなホストです。`src/` の本体にモデル呼び出しや接続管理を追加せず、examples 側が接続・transaction・時計・会話の出典・忘却ジャーナルを持ちます。Bun と開発依存だけで実行できます。

```sh
bun install --frozen-lockfile
bun run check:memory       # モデル不要。固定した判断を再生し、保存・取得・忘却を検査
bun run check:memory:live  # Codex SDK + gpt-6-luna。実際の意味判断も検査
bun run check:memory:conversations       # 会話シナリオ13種類・54工程の固定判断を再生
bun run check:memory:conversations:live  # 同じ会話シナリオをlunaで実験
bun run check:memory -- --suite holdout --live # 指示固定後に設計した未検証12ケース
bun run check:memory -- --suite all --live # 基本・会話・追加ケースをまとめて実験
bun run check:memory -- --suite conversation --scenario ambiguous-forget --live # 1ケースを再現
bun test test/examples    # 基盤自体の回帰試験。外部へのモデル呼び出しなし
bun run verify            # examples の型・整形・lint・回帰試験を含む全体検証
```

成功は終了コード 0、認証・モデル・契約・期待結果のいずれかの失敗は 1 です。失敗したシナリオの残りの工程は進めず、独立した別シナリオは続けます。認証・モデル通信の失敗や共通チェックの失敗では全体を止めます。実モデルが使えないときに固定応答へ切り替える処理はありません。レポートのシナリオ別結果には成功工程数と失敗工程を残し、未実行を成功に数えません。

## 何を確認するか

モデルを使わない共通チェック8項目は、Records の保存・冪等性・版の読み分け、principal / scope 制限、transaction の rollback、引用の不一致拒否、Records → State → 外部派生物の忘却、外部削除確認、墓標による再登録拒否、変更フィード、保持期限と失効、時間判定、再起動、古い DB の復元、ジャーナル追記直後のクラッシュ、ジャーナルの破損・欠落です。関連する確認をまとめて1項目と数えます。

その後に、同じホストで次の会話シナリオ9工程を実行します。

- 好みの保存 → 再起動後の参照 → 好みの訂正 → 仮定の話では書き換えない → 現在の好みを参照。
- 好みを過去の版ごと忘却 → 忘却前の DB を復元して再照合 → 再起動後にも思い出さない。
- 否定された好みの保存 → 再起動後の参照で否定を維持。

各参照は新しいモデルスレッドに質問と現在の State だけを渡します。過去の会話、期待結果、固定応答は渡しません。忘れた内容をモデルの会話履歴で答える経路を避けています。

会話用スイートは [conversations.ts](conversations.ts) にあり、次の課題を与えます。人物のIDと呼称の対応はホスト所有のカタログとして渡し、人物の好みや住まいといった正解は渡しません。

| シナリオID | 課題 |
|---|---|
| mixed-people-topics | 3人と複数話題の混在、一人の好みだけ訂正・忘却 |
| ambiguous-correction | 人物も確度も不明な訂正では変更を保留して確認 |
| ambiguous-forget | 誰の話か不明な忘却では確認し、明示後に一人分だけ消去 |
| local-exception | 今日だけの例外・未確定の予定で普段の習慣を変えない |
| negation-reversal-selective-forget | 否定から肯定への訂正と、別の好みだけの忘却 |
| quotes-fiction-injection | 架空の台詞・引用内の命令・現実の伝聞の区別 |
| same-name-different-people | 同姓の職場の人と近所の人を区別 |
| update-and-forget-in-one-turn | 一つの発話で訂正・保持・他者の忘却を実行 |
| unknown-and-false-premise | 質問の前提から未提供の事実を作らない |
| forget-topics-keep-exceptions | 複数の話題を忘れ、指定した例外と他者情報を保持 |
| same-name-explicit-both | 同姓の二人に「二人それぞれ」を明示した対照実験 |
| unknown-explicit-preference | 好みを「好き」と明示した状態での未知情報の扱い |
| forget-explicit-preference | 好みを明示した状態での複数話題の忘却と例外保持 |

曖昧な依頼は `clarification` に確認質問があることと変更がゼロであることを検査します。部分忘却は対象の過去の版が消え、対象外の履歴が変更されないことを検査します。復元試験も全件消去に限定せず、生き残る項目を含む履歴が一致することを確かめます。

この実験ではモデルの会話履歴を再利用しません。各発話を現在のStateと人物カタログから理解する検査であり、生の会話履歴を使う代名詞解決や会話管理の評価は含みません。

## offline と live の判定

offline は [scenarios.ts](scenarios.ts) の固定した構造化判断を再生します。`$active:0` はその工程の active item を指す fixture の記法です。発話から判断を作る仕組みではなく、ホストと公開 API の接続を確定的に検査します。日本語の理解精度を示すものではありません。

live は同じシナリオの発話を luna に渡し、構造化出力を公開 API へ接続します。保存する内容、分類、意味キー、訂正・忘却の対象は LLM が選びます。コードは契約、引用一致、UTF-8 範囲、対象 ID、CAS、アクセス権、ジャーナルの耐久化を検査します。自動的な保存はすべて `agent_inferred` です。ユーザー確認済みへ昇格させません。

保存・参照・意味評価はそれぞれ専用の指示を使います。モデルには人物IDとラベルを結合した項目を渡し、意味キー・値・版・期間の情報を保持します。件数・subject・kind・否定の極性はコードで一致を検査し、値の意味はsemanticKeyも含む事実として別の新規スレッドで評価します。「コーヒー」と「コーヒーが好き」のような表現差は許容し、別の好みへの変化や余計な事実は失敗とする指示です。人が定義した意味の正解文（`criterion`）も評価に渡し、否定された単語だけでは曖昧になる期待値を補います。意味評価は保存後の事実の比較に限定します。確認質問・操作数・忘却の範囲はコードで別に検査し、操作の解釈と状態比較を混ぜません。評価に期待結果と正解文を渡すのは判断・保存後だけで、評価結果から記憶を書き換えることはありません。空の期待結果は件数だけで確定的に判定します。

この意味評価も同じ luna による評価であり、人手で正解を保証した包括的な精度測定ではありません。判定理由と元の出力をレポートに残すため、誤判定を調べられます。語句の一致や個別の発話分岐で意味判断を代替しません。

## Codex の認証と分離

`@openai/codex-sdk` 0.163.0 を開発依存として固定しています。本体の実行時依存は増えません。モデルは `gpt-6-luna`、reasoning は medium、1回の呼び出しの制限は120秒です。標準シナリオは判断9回・意味評価7回で、Codex の利用枠を消費します。モデルの利用可否はアカウントに依存します。

- `CODEX_HOME`（未指定なら `~/.codex`）の `auth.json`。ログイン情報だけを一時ディレクトリへシンボリックリンクします。ファイル保存の資格情報がないキーチェーン専用環境では、キーかファイル形式の Codex ログインを用意してください。

実行中も工程ごとにレポートを保存します。外部からプロセスを強制終了した場合、`running` のままのレポートは未完了です。offline のモデル名とusageは null、モデル呼び出し数は0です。

チェック用の合成発話だけを使います。忘却はメモリー本体の論理消去を検査します。検証用に残した原文・レポート・忘却前のスナップショットや外部サービス上の記録まで消すものではありません。不要になった実行ディレクトリは削除してください。

新しいケースは [scenarios.ts](scenarios.ts) または [conversations.ts](conversations.ts) の配列へ追加します。`message`、`expected`（値・極性・kind・subject）、`criterion`（意味の正解文）、offline 用の `replay` を定義し、必要なら `restart` を指定します。fixtureでは `$key:<semanticKey>` で順序に依存せず既存項目を指定できます。`expectClarification` と `expectedActions` は確認質問の有無と操作数の検査用です。`restoreBeforeForget` は忘却後に古いDBを復元し、旧版の消去と対象外の保持も検査します。実装に発話専用の分岐を追加する必要はありません。対応する出力契約とLLM指示は [protocol.ts](protocol.ts) にあります。

このホストは1プロセス・逐次実行のチェック専用です。本番ホストの並列制御、実 Eumenes の結合、物理消去、World / Consolidation、日本語全般の精度はこの結果だけでは保証しません。

## ページをまたぐ根拠判断

`retrieval.ts` の `recallMemory(host, message, { candidates, grounding }, options)` は、公開APIから同一スナップショットを読み、ページごとに関連候補を残してから一度まとめて根拠を判断する。`withLuna` の `recall` 指示をそれぞれ `candidateInstructions` / `groundingInstructions` に差し替えた二つのクライアントを渡す。`subjects` で人物ラベルを渡せる。単一ページの根拠IDをそのまま合併しない。

結果には質問項目ごとの状態・根拠IDと、ホストが計算した `coverage` がある。`maxPages` / `maxCandidates` に達した場合、根拠不明の項目は `unresolved`。`unknown` も今回取得した根拠では確立できないという意味であり、世界や全記憶に存在しないという保証ではない。`coverage.complete` はページ走査が完了したことを表し、LLMによる候補選択の完全性を保証しない。通常の `main.ts` は従来の全件入力の比較基準を維持する。

```sh
bun examples/experiments/grounding.ts --live verification-reports/cycles/new-grounding
```

## 同じ事実・訂正・共存・矛盾の計画

`planning.ts` の `planMemory` は、既存の保存指示を拡張した `planningInstructions` を `withLuna` の `decide` に渡して使う。判断と書込は分離し、計画だけを返す。各提案を `new / same / supersedes / coexists / conflicts / forget` としてLLMが分類する。`same` と `conflicts` は実行対象にせず、未解決の矛盾は確認を要求する。訂正は既存の主体・種類・キーと置換IDを再利用し、共存は別のキーを要求する。忘却ではLLMが別キーの同義記憶も列挙し、コードが許可されたIDだけに展開する。

結果はモデルが参照した時点の `snapshotHash` を持つ。実行側は古い計画の適用を防ぐ必要がある。コードは同義判定を実装せず、LLMの分類の完全性は意味評価の対象として残る。

```sh
bun examples/experiments/identity.ts --live verification-reports/cycles/new-identity
```
