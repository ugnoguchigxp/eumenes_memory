# メモリー単体の動作チェック

Eumenes を起動せず、公開 API と実 SQLite ファイルを使って動作を確認する小さなホストです。`src/` の本体にモデル呼び出しや接続管理を追加せず、examples 側が接続・transaction・時計・会話の出典・忘却ジャーナルを持ちます。Bun と開発依存だけで実行できます。

```sh
bun install --frozen-lockfile
bun run check:memory       # モデル不要。固定した判断を再生し、保存・取得・忘却を検査
bun run check:memory:live  # Codex SDK + gpt-6-luna。実際の意味判断も検査
bun run check:memory:conversations       # 会話シナリオ13種類・54工程の固定判断を再生
bun run check:memory:conversations:live  # 同じ会話シナリオをlunaで実験
bun run check:memory -- --suite holdout --live # 指示固定後に設計した未検証12ケース
bun run check:memory -- --suite all --live # 基本・会話・追加ケースをまとめて実験
bun run check:memory -- --suite conversation --scenario ambiguous-forget --live # 1ケースを再現
bun test test/examples    # 基盤自体の回帰試験。外部へのモデル呼び出しなし
bun run verify            # examples の型・整形・lint・回帰試験を含む全体検証
```

成功は終了コード 0、認証・モデル・契約・期待結果のいずれかの失敗は 1 です。失敗したシナリオの残りの工程は進めず、独立した別シナリオは続けます。認証・モデル通信の失敗や共通チェックの失敗では全体を止めます。実モデルが使えないときに固定応答へ切り替える処理はありません。レポートのシナリオ別結果には成功工程数と失敗工程を残し、未実行を成功に数えません。

## 通常利用の入口

`bun run memory` は、100ケース比較で採用を決めた耐久実行器を使う。`plan` はLLMで計画を作り、まだ書き込まない。計画を保存してから `apply` で適用する。再試行には同じ操作IDと保存済み計画を渡し、再生成しない。

```sh
bun run memory /tmp/my-memory plan '和紙作りが好きです。覚えてください。' > /tmp/memory-plan.json
bun run memory /tmp/my-memory apply request-001 /tmp/memory-plan.json
```

`partial` / `failed` は終了コード1となる。`needs_clarification` は表示された確認が必要であり、全変更の成功を意味しない。保存した計画には発話が含まれるので呼出し側で管理する。`check:memory` は従来方式の比較・回帰検証用で、通常利用はこの入口を使う。実行器自体は [execution.ts](execution.ts)、採否の根拠は [100件比較](../experiments/holdout-100/RESULTS.md)。

## 何を確認するか

モデルを使わない共通チェック8項目は、Records の保存・冪等性・版の読み分け、principal / scope 制限、transaction の rollback、引用の不一致拒否、Records → State → 外部派生物の忘却、外部削除確認、墓標による再登録拒否、変更フィード、保持期限と失効、時間判定、再起動、古い DB の復元、ジャーナル追記直後のクラッシュ、ジャーナルの破損・欠落です。関連する確認をまとめて1項目と数えます。

その後に、同じホストで次の会話シナリオ9工程を実行します。

- 好みの保存 → 再起動後の参照 → 好みの訂正 → 仮定の話では書き換えない → 現在の好みを参照。
- 好みを過去の版ごと忘却 → 忘却前の DB を復元して再照合 → 再起動後にも思い出さない。
- 否定された好みの保存 → 再起動後の参照で否定を維持。

各参照は新しいモデルスレッドに質問と現在の State だけを渡します。過去の会話、期待結果、固定応答は渡しません。忘れた内容をモデルの会話履歴で答える経路を避けています。

会話用スイートは [conversations.ts](conversations.ts) にあり、次の課題を与えます。人物のIDと呼称の対応はホスト所有のカタログとして渡し、人物の好みや住まいといった正解は渡しません。

| シナリオID | 課題 |
|---|---|
| mixed-people-topics | 3人と複数話題の混在、一人の好みだけ訂正・忘却 |
| ambiguous-correction | 人物も確度も不明な訂正では変更を保留して確認 |
| ambiguous-forget | 誰の話か不明な忘却では確認し、明示後に一人分だけ消去 |
| local-exception | 今日だけの例外・未確定の予定で普段の習慣を変えない |
| negation-reversal-selective-forget | 否定から肯定への訂正と、別の好みだけの忘却 |
| quotes-fiction-injection | 架空の台詞・引用内の命令・現実の伝聞の区別 |
| same-name-different-people | 同姓の職場の人と近所の人を区別 |
| update-and-forget-in-one-turn | 一つの発話で訂正・保持・他者の忘却を実行 |
| unknown-and-false-premise | 質問の前提から未提供の事実を作らない |
| forget-topics-keep-exceptions | 複数の話題を忘れ、指定した例外と他者情報を保持 |

曖昧な依頼は `clarification` に確認質問があることと変更がゼロであることを検査します。部分忘却は対象の過去の版が消え、対象外の履歴が変更されないことを検査します。復元試験も全件消去に限定せず、生き残る項目を含む履歴が一致することを確かめます。

この実験ではモデルの会話履歴を再利用しません。各発話を現在のStateと人物カタログから理解する検査であり、生の会話履歴を使う代名詞解決や会話管理の評価は含みません。

## offline と live の判定

offline は [scenarios.ts](scenarios.ts) の固定した構造化判断を再生します。`$active:0` はその工程の active item を指す fixture の記法です。発話から判断を作る仕組みではなく、ホストと公開 API の接続を確定的に検査します。日本語の理解精度を示すものではありません。

live は同じシナリオの発話を luna に渡し、構造化出力を公開 API へ接続します。保存する内容、分類、意味キー、訂正・忘却の対象は LLM が選びます。コードは契約、引用一致、UTF-8 範囲、対象 ID、CAS、アクセス権、ジャーナルの耐久化を検査します。自動的な保存はすべて `agent_inferred` です。ユーザー確認済みへ昇格させません。

保存・参照・意味評価はそれぞれ専用の指示を使います。liveの保存出力は、依頼ごとの`coverage`（対象・根拠・`change / retain / clarify / ignore / constraint`・既存ID・操作番号）を先に返し、続けて`actions`を返します。ホストは変更と操作、保持と既存ID、確認と質問の対応、および全操作への参照を検査します。網羅した依頼自体が正しいかはLLMの判断であり、この構造だけで意味的な取りこぼしを防ぐ保証はありません。固定判断のoffline再生と通常利用の計画APIの出力契約は従来のままです。保存と参照には人物IDとラベルを結合した項目を渡し、意味キー・値・版・期間を保持します。保存は人物を決めてから分類し、他者の情報は内容にかかわらず`other_person_note`とします。訂正では既存の属性と意味キーを維持し、出来事によって変わった現在の値を保存します。参照の出力は`answers: [{request, itemIds}]`です。LLMが質問を回答可能な部分に分け、未知の部分を空配列にして、答えられる部分を残します。コードは返された許可済みIDを合併します。訂正・忘却・参照のIDは、その時点のactive項目に出力スキーマで制限します。

評価はまず件数・subject・kind・否定の極性を厳密に検査し、同じsubject・kind・極性の組へ機械的に分けます。値も文字列の多重集合として完全一致する組は、その一致を採用します。表現が違う組だけを新規のlunaスレッドへ渡し、組ごとの同義判定を求めます。v25の出力は組内の事実IDを一対一で対応づけた`matches`です。各対で両側の全文引用、関係の分類と記述、明示された限定、独立した主張ではない連想を分け、期待側からの不足`missingFromActual`と実際側からの不足`missingFromExpected`を返します。両方向の不足リストが全対で空のときだけ成功です。重複する真偽値は返しません。ホストはID・全文引用・対応の全件性・出力の形だけを検証し、意味の同一性をコードで決めません。日本語の言い換えはLLMが判断し、数量・条件・例外の欠落、余計な意味は失敗にします。

意味評価への入力はsubject・kind・人物ラベル・比較する実際値と期待値です。共通の外側の極性は厳密な構造検査で一致した後に入力から除き、本文は変更しません。既存の`criterion`は各組の`relationContext`として渡し、省略された主体や裸の好みの関係を理解する補助とします。明示された述語の置換、限定の補完、否定の再適用は許可しません。ただしv25の実測でも、この境界を評価器が越える誤りが観測されています。原文・意味キー・履歴は監査用の`audit`に残し、評価器には渡しません。原文引用はアクセス権・版・ダイジェスト・UTF-8範囲を検証して取り出します。評価には渡しません。期待値は判断・保存の入力に含めず、評価結果から記憶を書き換えることもありません。確認質問・操作数・忘却範囲と復元は従来どおり別に検査します。空の期待結果は件数で確定的に判定します。

この意味評価も同じ luna による評価であり、人手で正解を保証した包括的な精度測定ではありません。判定理由と元の出力をレポートに残すため、誤判定を調べられます。語句の一致や個別の発話分岐で意味判断を代替しません。

## Codex の認証と分離

`@openai/codex-sdk` 0.163.0 を開発依存として固定しています。本体の実行時依存は増えません。モデルは `gpt-6-luna`、reasoning は medium、1回の呼び出しの制限は120秒です。標準シナリオは判断9回で、表現が期待値と異なる組には追加の意味評価を行います。実行はCodex の利用枠を消費します。モデルの利用可否はアカウントに依存します。

このホストは1プロセス・逐次実行のチェック専用です。本番ホストの並列制御、実 Eumenes の結合、物理消去、World / Consolidation、日本語全般の精度はこの結果だけでは保証しません。

## 一括取得

`retrieval.ts` の `recallMemory(host, message, complete, { subjects })` は許可された全記憶を一度だけモデルへ渡す。`withLuna` の `recall` 指示には `groundingInstructions` を使う。候補選択・ページ分割・候補数の予算は通常利用から削除した。

```sh
bun run memory /tmp/my-memory recall '私について何を覚えていますか？'
```

結果は質問項目ごとの `supported / unknown / conflict` と根拠ID。`coverage` は全件を渡したことと件数を示し、モデル判断の完全性を保証しない。入力上限や通信の失敗はエラーとして返し、黙って一部を切り捨てない。1001件までは前回比較で一括方式が同等以上だったが、無制限の入力長を保証するものではない。

取得の指示では、主体・時期・条件をそろえてから矛盾を判定し、明示的な否定も回答根拠として扱う。適用できる例外は一般則より優先し、適用条件が分からなければ不明にする。新規100件は78→95件、既知回帰20件は10→19件だったが、複数質問の統合や根拠IDの誤写などは残る。[比較と残る問題](../experiments/one-shot-holdout/RESULTS.md)を参照。

旧ページ方式は `examples/experiments/frozen-retrieval.ts` と `frozen-support.ts` に凍結し、過去の比較スクリプトだけが参照する。通常利用側から実験コードは呼ばない。過去のmanifestは当時のコミットのソースを識別するもので、参照先を移した現在の実験ファイルのハッシュではない。

## 同じ事実・訂正・共存・矛盾の計画

`planning.ts` の `planMemory` は、既存の保存指示を拡張した `planningInstructions` を `withLuna` の `decide` に渡して使う。判断と書込は分離し、計画だけを返す。各提案を `new / same / supersedes / coexists / conflicts / forget` としてLLMが分類する。`same` と `conflicts` は実行対象にせず、未解決の矛盾は確認を要求する。訂正は既存の主体・種類・キーと置換IDを再利用し、共存は別のキーを要求する。忘却ではLLMが別キーの同義記憶も列挙し、コードが許可されたIDだけに展開する。

結果はモデルが参照した時点の `snapshotHash` を持つ。実行側は古い計画の適用を防ぐ必要がある。コードは同義判定を実装せず、LLMの分類の完全性は意味評価の対象として残る。

```sh
bun examples/experiments/identity.ts --live verification-reports/cycles/new-identity
```

## 計画の事前検査・まとめた実行・再試行

`execution.ts` の `applyMemoryPlan(host, operationId, plan)` で計画を適用する。同じ依頼の再試行には同じ操作IDと計画を渡す。別の計画に同じIDを使うと拒否する。最初の実行では計画時点の記憶と照合し、全操作を既存APIで試行して巻き戻し、契約違反を実行前に検出する。事前検査では原文ログと忘却ジャーナルを追記しない。

依存する変更の `groups` はLLMが選ぶ。保存だけのグループは状態変更と完了記録を同じSQLite transactionで確定する。途中失敗ならグループ全体を巻き戻す。独立したグループが先に完了していれば、その結果は保持し、再試行で繰り返さない。矛盾を含むグループは全体を保留する。`completed / needs_clarification / partial / failed` と各グループの結果を返し、途中失敗後の未実行分も明示する。前提違反・古い計画は例外となる。

忘却だけのグループは、旧版を含む対象IDを先に保存し、既存の耐久ジャーナルで対象ごとに実行する。途中停止後はホストを開き直してジャーナルを照合し、同じ操作IDで残りを実行できる。忘却は一括の巻き戻しを保証しない。保存と忘却が混在する同一グループは実行前に拒否する。両方の不可分な実行が必要なら、モデルは提案を控えて確認を求める。

完了記録はホスト所有の `example_memory_operation` 表に保存し、元発話や記憶本文を複製しない。実行中の状態確認にはIDとハッシュを用い、対象忘却以外の外部変更があれば再計画を要求する。この実装は1プロセス・逐次実行用。完了結果はその操作の履歴であり、その後も記憶が変わらない保証ではない。古いDBへ戻すと完了記録も戻るため、任意のバックアップ復元をまたぐ一度限りの実行は保証しない。忘却ジャーナルの再適用は従来どおり必要。実行失敗時に原文ログが残る場合があり、ログを含む物理消去はホストの責任となる。

```sh
bun examples/experiments/execution.ts --live verification-reports/cycles/new-execution
```
