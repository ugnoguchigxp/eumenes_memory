# メモリー改善の分離実験

既存の `standalone` を実行基盤として再利用し、生成・採点・回答根拠・候補取得を別々に比較する。通常のプロトコルの版は変更しない。応答を読む処理も `frozen-protocol.ts` に固定し、通常側の応答形式変更の影響を受けない。保存・権限・忘却・復元には公開 API と実際の SQLite を使う。

## 実行

リポジトリ直下で実行する。live は既存の Codex 認証と `gpt-6-luna` / medium を使う。出力先は実行ごとに別ディレクトリにする。

```sh
bun examples/experiments/factorial.ts --live verification-reports/experiments/new-factorial
bun examples/experiments/answers.ts --live verification-reports/experiments/new-answers
bun examples/experiments/scale.ts --offline verification-reports/experiments/new-storage
bun examples/experiments/scale.ts --live verification-reports/experiments/new-scale
```

`report.json` には事前に固定したケース、指示、schema、入力、入力ハッシュ、応答、token 数、呼出し時間、検査結果を保存する。接続失敗は意味判断の失敗と分け、処理中の呼出しを回収してから停止する。成功した入力だけを再生成して結果を差し替えない。

## 比較の契約

| 実験 | 固定するもの | 比較するもの | 判定 |
| --- | --- | --- | --- |
| factorial | 入力、保存 API、モデル、同一生成出力 | v9/v10 の生成指示と評価指示・評価入力 | 参照 ID、保存契約、構造、評価器の合否を別集計 |
| answers | 新規の6ケース、モデル、供給された事実 | v10のID列挙と、要求項目ごとの supported / unknown / conflict + 根拠ID | 両方式の根拠ID集合、および構造化方式の状態と根拠の組 |
| scale offline | 実際の公開保存・取得・忘却 API | 999 / 1000 / 1001 / 10000件 | 全件到達、重複なし、忘却後の古いDB復元での非復活 |
| scale live | 同じ許可済み集合、同じ問い、同じ最終参照指示 | 最新1000件、全件、250件ずつ全走査、ページ要約による候補選択 | 正解ID、候補到達、呼出し数、token、時間 |

`prompts.json` は保存済みレポートから抽出した v9/v10 の指示・schema と出典ハッシュ。v10評価器には元の仕様どおり発話も渡すため、「評価指示だけ」の差ではなく**評価指示＋入力の組**の差を測る。生成物を両方に渡すことで、生成側との混同を避ける。

生成・参照・回答根拠は各ケース3反復。反復は同じ会話の揺れを見るもので、独立した新規ケースとして一般精度を推定しない。大規模LLM比較は100件と1001件、各3質問の1回ずつであり、探索的な測定にとどめる。10000件の意味検索精度は未測定。

## 取得方式

`listState` の `nextCursor` がある場合、未取得の記憶がある。`after` を渡して続きを取得する。同じフィルターと権限を維持し、同じ read transaction 内で列挙すると一貫した集合になる。各ページの上限1000は維持する。`StandaloneHost.list()` は全ページを取得し、1000件より古い事実の参照・訂正・忘却も可能にする。全件をLLMの入力枠に収められるかは別の制約であり、件数に応じた候補取得は以下で比較する。カーソルは認可を代替せず、毎回権限・忘却を検査する。

`latest-1000` は従来の欠落を測る対照群。`all` は全ページを列挙して1回のLLM入力にする。`page-scan` は全ページをLLMに渡してIDを合併する。これは探索漏れを防ぐ基準方式だが、複数ページの関係を統合した最終回答までは検証しない。

`directory` は、各250件をLLMが600文字以内の索引用要約にし、質問に対応するページをLLMが選び、選ばれた**元の事実**から根拠IDを選ぶ。コードは意味を分類しない。索引構築コストと問合せコストを分けて記録する。要約は一回の固定スナップショットから作る実験用の一時データで、運用用の永続索引ではない。永続索引に進む場合は、変更フィード・外部派生物登録・忘却と復元の追従検証が別途必要。

## 今回の採点修正

最初の factorial 実行には、正解側に仮の `semanticKey` まで送る不備があった。元の standalone 評価契約では正解側にこのフィールドはない。生成とID照合は影響を受けないが、初回の意味採点は比較から除外する。元レポートを残し、`regrade.ts` で**同じ生成結果**を正しい契約で再採点した。正解の文章・主体・種類・極性、評価指示・schemaは変更しない。

```sh
bun examples/experiments/regrade.ts verification-reports/experiments/factorial/report.json verification-reports/experiments/new-corrected-judge
```

この補正専用コマンドは54件の生成応答が揃っていることを確認する。初回末尾の採点1件が接続エラーでも、全生成応答が保存されていれば同じ入力を再採点できる。新規 factorial はすでに正しい契約を使うため補正不要。

「楽しみ」と「趣味」の同値性は曖昧な正解境界として別掲し、評価器の正確さの校正から除く。校正は同義・頻度欠落・人物取り違えを用いる。構造化根拠の検査は状態とIDの対応までであり、最終的な自然文回答の正確さを保証しない。

## 採用条件と残る検証

欠落・アクセス漏れ・忘却復活は検証集合で0件を要求する。追加の表現や取得構造は品質と呼出し・token・時間を併記し、精度向上を確認できない場合は既存方式を維持する。今回の対象を超える24会話×3反復の広い評価、似た人物や事実、複数ページの関係、期間・訂正、最終回答、永続索引の更新・忘却・復元は次の採用判定に必要。
