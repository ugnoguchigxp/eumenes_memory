# 2026-10-16 改善・比較結果

v10の改善は生成側に実体があり、評価器の変更だけによる見かけの改善ではなかった。1000件での取得打ち切りも実測できたため、公開APIのページ取得と通常例の全件列挙を実装した。質問別の根拠表現と要約による候補取得は比較可能な実験として残す。

集計は [results/2026-10-16.json](results/2026-10-16.json)、再実行手順と範囲は [README.md](README.md)。生データは `verification-reports/experiments/`。固定した合成ケースを `gpt-6-luna` / medium / SDK 0.163.0 で実行した。一般的な精度を保証する規模ではない。

## 1. v10の生成側と評価側

参照6ケースと保存3ケースを各3回実行。保存の同じ出力をv9/v10の評価器へ交差投入した。v10評価器には元の仕様どおり発話も渡すため、評価指示と入力を合わせた変更として扱う。

| 指標 | v9生成 | v10生成 |
| --- | ---: | ---: |
| 参照IDの正答 | 7/18 | 18/18 |
| 保存APIの契約適合 | 6/9 | 9/9 |
| v9評価器での保存合格（契約拒否を失敗に含む） | 5/9 | 7/9 |
| v10評価器での保存合格（同上） | 5/9 | 7/9 |

v9の3件の契約拒否は人物と種類の不整合。v10では解消した。構造検査は契約適合した全出力で成功。同じ保存出力への評価器の合否は15組すべて一致した。したがって、この集合では生成側の改善と評価側の変更を分離できる。

評価器だけの校正は、同義・頻度欠落・人物取り違えの3ケース×3反復。v9が8/9、v10が9/9。v9は同義の正しい記録を、正解側に意味キーがないという理由で1回不合格にした。誤合格はこの校正集合では両方0/6だが、母数は小さい。

「パン作りが楽しみ」と「趣味」の同値性は評価器間・反復間で揺れたため、校正の正確さから除外した。生成物の合否表には事前の基準どおり残す。この論点を解消したという結論にはしない。正解表現の曖昧さを、生成品質の低さと同一視しないことが必要。

初回の採点入力には、正解側に仮の意味キーを付ける不備があった。この意味採点は無効として保存し、生成済みの全出力を変更せずに、元の評価契約へ戻して再採点した。初回末尾の採点1件は接続エラー（403）で停止したが、生成54応答はすべて取得済み。修正後の54採点は完了した。生成のやり直しや正解の緩和はしていない。

## 3. 大量記憶の取得

100件では4方式とも3/3問。1001件では、古い・中間・新しい位置に置いた3つの事実について以下の結果になった。ページ走査と要約索引は250件単位。すべて同じ最終参照指示で、ページや候補集合を全記憶と誤認しない入力契約を使う。

| 1001件での方式 | 正答 | 問合せのLLM呼出し合計 | 入力token合計（3問） | 問合せ時間中央値 |
| --- | ---: | ---: | ---: | ---: |
| 最新1000件のみ | 2/3 | 3 | 294,405 | 14.9秒 |
| 全件入力 | 3/3 | 3 | 294,657 | 11.2秒 |
| 全ページ走査 | 3/3 | 15 | 447,681 | 55.0秒 |
| ページ要約から候補取得 | 3/3 | 6 | 115,428 | 24.4秒 |

最新1000件のみの方式は最古の事実を取得できず、不正答だった。全件入力は今回の規模で最も速く、ページ走査は入力枠を抑えながら全範囲を探す基準方式として使える。単純なページ分割だけではtoken削減にならず、複数回の固定入力の負担が増えた。

要約方式は、索引作成に別途5呼出し、入力137,638 token、約49.6秒を要した。候補は各問1件・250件・250件で、3問とも正解を含む。問合せ入力だけなら全件入力より約61%減り、索引構築を含む3問合計でも約14%減った。ただし問合せは遅く、初回の構築時間もある。100件では要約方式の問合せ入力自体が増えた。少量の記憶に一律に索引を挟む根拠はない。

tokenはSDKの固定入力とキャッシュを含み、金額ではない。時間は並行実行下の少数実測で、厳密な速度比較ではない。対象事実は繰り返しの多いダミー群の中で目立つため、似た事実が多数ある実環境への一般化は避ける。

## 4. 採用した変更

- `listState` に `after` / `nextCursor` を追加。並び順は従来どおり更新順降順・ID昇順。1ページ1000件の上限は維持し、続きの有無を明示する。
- `StandaloneHost.list()` は同一read transaction内で全ページを取得。古い事実の参照・訂正・忘却に到達する。
- 実験の指示差替えは既存 `withLuna` を拡張して再利用。通常側で並行して行われているプロトコル更新は保持する。
- 実験の指示・schema・応答parserを固定し、生成と採点の分離、状態付き根拠、ページ走査、要約による候補選択を再実行可能にした。

保存形式・DB schema・意味キー規則は変えていない。意味の分類・要約・候補選択はLLMが行い、コードはページ取得、権限、契約、許可されたID、集計を扱う。語句や個別ケースで意味判断を置き換える製品分岐は追加していない。

999 / 1000 / 1001 / 10000件の保存・全件取得・忘却・古いDBからの復元を通過した。最終実行で10000件の列挙は約48ms、忘却後の復元は9999件で非復活を確認。これはストレージ試験であり、10000件をLLMで検索した結果ではない。

## 5. 次の採用判定

当面は、全件が入力枠に収まる場合は全件取得を基準にする。項目別の根拠形式は、不明・矛盾を利用者に伝える最終回答と組み合わせて検証する。要約索引は反復問合せのtoken削減候補として維持するが、標準の永続索引にはまだ組み込まない。

次は、類似した事実・同姓人物・複数ページをまたぐ質問で索引の取りこぼしを測り、未取得と本当の未知を区別する。その後、既存の変更フィードと外部派生物管理を使って、索引の更新・忘却・復元を通す。24会話×3反復の広い検証と自然文回答までの評価は、この対象別パイロットの次段階であり、今回完了したものには数えない。
